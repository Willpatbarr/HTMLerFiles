Must Know

Three stages, one artifact

Stage 1 — frontend

Builds the bundle from a BuildKit named context, so the separate repo needs no clone, no network, no credentials.

Stage 2 — Go

Cross-compiles for $TARGETARCH from a native builder. Nothing runs under QEMU — arm64 costs what amd64 does.

Stage 3 — ship

Distroless, nonroot. No shell, no package manager, no libc. Three binaries and the embedded bundle.

Two things that are easy to miss

  • /migrate and /reindex ship with the server. Not a convenience — a database built before LAM-10 needs migrate baseline before the server will start, and there's no shell here to fetch a binary with.
  • The binary healthchecks itself. Distroless has no curl, so /laminarflow healthcheck asks the server over loopback. It answers before config loads, so it never needs DATABASE_URL.

Decisions I Made

You were away, so I decided these myself. Each one with the alternative, in case you want it changed.

2 · Distroless base image

gcr.io/distroless/static-debian12:nonroot. No shell, no package manager, no libc — only CA certificates, timezone data, and a nonroot user.

Why: the service is exposed to a tailnet. A shell in the image is attack surface that buys convenience you can get other ways.

Alternative

alpine:3 if you want docker exec sh. It is one line in the final stage. docs/deploy.md documents debugging without a shell — logs, psql in the db container, /migrate status — so read that before switching.

3 · BuildKit named context for the frontend

The frontend arrives as --build-context frontendsrc=../LaminarFlow-Frontend rather than being cloned during the build.

Why: repos stay independent, and the build needs no network access and no credentials — which matters if either repo ever goes private.

Alternatives

Clone the repo in-build (needs network, and auth for a private repo), or require build-frontend.sh to have run first (the image build stops being self-contained).

4 · Ship /migrate and /reindex in the image

Three binaries, not one.

Why: a database built before LAM-10 needs migrate baseline before the server will start. With a shell-less image and no /migrate, that would be impossible from the container.

Alternative

Server-only image, running migrations from outside the container. Smaller image, but the operator needs a matching binary on the host.

12 · rm -rf node_modules dist before npm ci

The frontend stage copies the whole checkout, then deletes the build artifacts before installing.

Why: named contexts have no .dockerignore of their own, so a host node_modules — built for macOS arm64 — would otherwise poison a Linux build.

Alternative

Add a .dockerignore to the frontend repo and copy selectively. Better layer caching, but it is a second PR in the other repo, and a new top-level file there would silently stop being copied.

5 · healthcheck subcommand on the binary

HEALTHCHECK CMD ["/laminarflow", "healthcheck"] — the binary asks itself over loopback.

Why: distroless has no curl. It also answers before config loads, so it needs no DATABASE_URL, and it hits /healthz not /healthz/db — a database blip should not restart a healthy process.

Alternatives

No HEALTHCHECK at all, or an Alpine base with curl available.

6 · Separate deploy/docker-compose.yml

The repo-root compose file still starts only Postgres for development.

Why: a developer running docker compose up should not accidentally start a server, and an operator reading the deploy file should not wade through dev-only settings.

Alternative

One file with compose profiles. Fewer files, but every reader has to know which profile they are in.

7 · APP_BIND defaults to 127.0.0.1

The published port binds loopback unless you say otherwise.

Why: Tailscale routes to loopback; a LAN does not. So the app is reachable over the tailnet without being exposed to whatever else is on the local network.

Alternative

0.0.0.0 if you want LAN access by default. It is one line in deploy/.env, no image rebuild.

8 · Postgres publishes no host port

The app reaches it over the compose network only.

Why: there is no reason to put a database on the tailnet. docker compose exec db psql covers the access you actually need.

Alternative

Publish 5432 if you want to connect a GUI client from your laptop over Tailscale.

9 · MIGRATE_ON_STARTUP=true in the deploy stack only

The binary still defaults to off; the compose file turns it on.

Why: an operator pulling a new image expects the schema to follow. Nothing else inherits the setting, so a dev run is unaffected.

Alternative

Keep it off everywhere and run /migrate up as a deliberate step. Safer, two-step upgrades over Tailscale.

11 · No BASE_URL or storage-path config

The ticket's step 3 lists them, but neither exists in the code yet.

Why: nothing builds an absolute URL — same-origin serving means relative paths — and there are no file uploads. An unused setting is one more thing that can be wrong. This is written down in the portability audit rather than left silent.

Alternative

Add the slots now so the shape is reserved. I would add them with the first feature that reads them.
