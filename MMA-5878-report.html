What changed

Event Details grew a QR action for public events, and a new screen behind it renders the event’s server-provided link as a code, writes it to a document the user picks, or hands it to the share sheet as a PNG.

The encode is deliberately cheap to reason about: one use case turns a string into a bitmap on the default dispatcher, and returns a Result rather than throwing, so a failure surfaces as a retry instead of taking the screen down.

Why the icon is gated three ways

The QR action appears only when an event is public, its calendar is editable, and its link is non-blank. The first two are the server’s authorization answer; the third is practical — the code encodes that link and nothing else, so without one the screen has nothing to draw. Share beside it follows the same link rule, which is where the shape came from.

That third condition is why there is no empty state. A link-less event cannot reach the screen, so a failed encode and a deleted event fold into one error with a retry rather than earning a designed state each.

Why the encode is not keyed on the event row

The state is driven by the link and the name alone. getEventDetailsFlow applies distinctUntilChanged to the whole joined row, so keying the encoder off the row would let any unrelated column changing under a background sync restart it — blanking a displayed code back to a spinner while someone holds the phone up to be scanned.

The shared state also carries a stop timeout, and the view model keeps the last rendered code. Both exist for the same window: the screen collects with lifecycle awareness, so a trip to the file picker stops the flow, and the save path resumes after CreateDocument has already created the file.

Where the route lives

Navigation 3 addresses every destination by key, so the screen needs one whether or not anything outside the feature reaches it. The only decision was where to declare it.

If the route is…The key goes inThis one
Deep-linkablea MaltSync NavSpec in the shared libraryno
Reached from another module:feature:calendar:apino

Event Details is the only caller and it lives in the same module, so EventQrNavKey stays feature-private and joins seven siblings already registered by hand in navKeySerializers. It moves to the api module the day a second module needs to name it.

Risks

The share grant is the part most likely to break silently. A missing ClipData or read flag still works on whichever chooser target a tester happens to pick, and fails on others, so the new test asserts both grant paths rather than just that a chooser comes back.

The stop timeout narrows the window where an export outlives its state; it does not close it. Past the timeout the flow stops, and on return the code re-encodes. The cached last rendered code is what keeps a save landing in that window from failing.

Staged share files accumulate one per shared event in the app cache. Each call now drops anything older than a day, which bounds the directory without risking a file an open chooser is still reading.

Questions for review

  1. Event Details hosts the QR action rather than the post-publish screen FR-7 names. That follows from the publish flow being out of scope — worth confirming it reads as intended and not as a missed requirement.
  2. Share sends the image alone. FR-8 and Test 10 ask for the image, and the URL case is MMA-5886, so adding link text here would reach into that ticket.
  3. The screenshot test uses the module’s standard single-device annotation, so the widthIn ceiling on the code never engages in a golden. Widening it is a module-wide decision, not this change’s.
Two failures that are not this change

:291-305

kotlin
override fun getShareImageIntent(uri: Uri, subject: CharSequence, text: String?): Intent {
 +  val send = Intent(Intent.ACTION_SEND).apply {
 +      type = IMAGE_MIME_TYPE
 +      putExtra(Intent.EXTRA_STREAM, uri)
 +      clipData = ClipData.newRawUri(null, uri)
 +      addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
