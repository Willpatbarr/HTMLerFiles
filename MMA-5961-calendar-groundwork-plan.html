MMA-5961 — Calendar: Groundwork & Restructuring

The foundation ticket for the calendar multi-view feature. Stand up the plumbing every grid view needs — without changing what the user sees yet.

Type: New Feature Epic: LTS-2600 Spec: MMA-5930 (SPEC.md) Blocks: MMA-5962 / 5963 / 5964 Reference impl: MMA-5930-2-CalendarFromPMG

Take the PMG prototype's foundation and make it production-real — restructure agenda into a "Schedule" view, wire live data + one shared repo-backed filter, add the rollout flag, shared loading/error + cross-view date state, and past-data sync — so 5962–5964 can build the actual grid views on top.

Remember Only 3 Things

1 — Nothing visible changes

With the rollout flag OFF the calendar looks exactly like today: Schedule only, selector hidden. This ticket is invisible-by-design plumbing.

2 — Kill the sample data

Both USE_SAMPLE_DATA flags come out, the sample/ package is deleted, real repo flows get wired in.

3 — One shared, durable filter + state

Filter writes the repo displayed flag (user's toggle wins). Focused date + loading/error live in one shared host, not per-view.

Context Optional

The prototype on MMA-5930-2-CalendarFromPMG renders sample data, keeps shared view code inside agenda/, has no rollout gate, an in-memory grid filter that does nothing on real data, and no sync-error feedback. The repo also syncs current-month-forward only.

This ticket does not build the Day/3-Day/Week/Month grids — those are 5962–5964. It builds everything underneath them so those tickets drop in cleanly.

Spec Coverage — FRs & ACs for this ticket

Word-for-word from the in-repo spec: feature/calendar/spec/viewsspec/spec.md (§5 Functional Requirements, §10 Acceptance Criteria). Note: spec.md's numbering differs from calendar-spec.html — the standalone rollout-flag FR was folded into FR-1, so local-first/snackbar is FR-24 here.

Functional Requirements this ticket completes (8)

FR-1
When the rollout flag is enabled (FR-24), the system shall provide five calendar view modes — Schedule, Day, 3-Day, Week, and Month — selectable from a view-mode selector available in every view. (When disabled, only Schedule shows and the selector is hidden — FR-24.)
FR-2
The system shall open to the Schedule view on each launch.
FR-3
The system shall display live calendar events from the repository in all five views.
FR-7
The system shall provide a calendar color filter (chip + bottom sheet) in every view.
FR-8
The system shall use a single shared, repository-backed filter across all views: toggling a calendar in any view writes the repository "displayed" flag (the same mechanism the Schedule chip already uses), so the change applies to every view and persists across restarts. (Codex M3 — on real data the grid chip currently writes an in-memory sample set and has no effect; it must share Schedule's repo-backed filter.)
FR-17
The system shall determine a calendar's initial visibility from its repository "displayed" flag (server/subscription-driven); a newly synced calendar follows its synced flag on first arrival. Thereafter the user's toggle wins — a later sync shall not overwrite a calendar the user has explicitly hidden or shown (the toggle is pushed to the server via UPDATE_ATTRIBUTES_ONLY, as the agenda does today). (Codex #4, A6)
FR-19
The system shall preserve the focused date across all views including Schedule (switching to Schedule scrolls the list to that date; switching from Schedule uses the list's current date). (Codex #7; Schedule inclusion is new — prototype excludes it)
FR-24
The system shall render grid views local-first from the database with no blocking loading spinner (an empty grid means no events, matching Schedule and Google Calendar). On a sync failure, the system shall show a non-blocking snackbar (no retry action for now) in all views including Schedule, while leaving already-loaded events visible. (Codex #2, A12 resolved. Intentional improvement over the agenda, which surfaces NO sync-error feedback today — including Schedule here also fixes that gap; reuse the app's existing HandleSnackbar / SnackbarUiModel + NavigationScaffold(snackbarHost=…), as OrganizationScreen does. Detecting failure = branch on WorkInfo.State.FAILED in the worker-info observer, which the agenda currently ignores.)

Acceptance Criteria this ticket should cover (5)

AC-1
(QA #1) — View switching & default. Given the calendar opens, When it first loads, Then the Schedule view is shown and the view-mode selector offers Schedule, Day, 3-Day, Week, and Month. (FR-1, FR-2)
AC-2
(QA #2) — Real events render in the grids. Given synced calendar events exist, When the user opens Day / Week / Month, Then each event appears on its correct day and time. (Multi-day / all-day event routing is covered by AC-3.) (FR-3, FR-4)
AC-6
(QA #6) — Single shared filter (both directions). Given multiple calendars, When the user toggles a calendar off in any view, Then its events hide in all views and the change persists across an app restart; And When the user toggles it back on, Then its events reappear in all views; And a calendar's initial visibility follows its repository "displayed" flag. (FR-7, FR-8, FR-17)
AC-14
(QA #14) — Cross-view date continuity (both directions). Given a focused date in a grid view, When switching to Schedule, Then the list scrolls to that date; And given Schedule scrolled to a date, When switching to a grid view, Then that grid opens on the same date. (FR-19)
AC-18
(QA #19) — Local-first load & sync-failure snackbar. Given no cached data yet, When a view loads, Then it renders from the database with no blocking spinner; And given a sync fails in any view (including Schedule), Then a non-blocking snackbar (no retry action) appears while already-loaded events remain visible. (FR-24)

Also in scope but not FR-numbered in spec.md: the §6 restructure (agenda → Schedule, shared code out of agenda/), the §9 data window (past-data sync + bounded date-range DAO query), and the smoke-test fix (§8 ship gates) — see the workstreams above.
