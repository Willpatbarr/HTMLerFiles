Routing today is by the allDay flag only (timedEvents() / allDayEvents() in grid/CalendarGridMeasurements.kt). The spec routes by duration too:

  • Change lands in the shared measurement/use-case layer (CalendarGridMeasurements.kt + GetCalendarGridUiStateUseCase.kt) — Week/3-Day pick it up for free.
  • Clip segments at window edges; DST-transition days must position correctly (see WS6).
2Chips — "render what fits"Must Know

FR-22 · AC-16

grid/CalendarGridEventChip.kt currently renders name + start time (with DateFormat.is24HourFormat). Spec rules:

  • Name always (ellipsize as needed).
  • No start/end times — ever. Delete the time line (the 12/24h handling stays available for hour labels, not chips).
  • Location only if the chip is tall enough — height-driven, so sub-30-min-at-min-height chips show name only.

Decide "tall enough" from the measured chip height vs. line heights (the chip already knows its duration-derived height from the measurements layer).

3Scroll — open at now + cross-view memoryMust Know

FR-18 · AC-13

Nothing controls the grid's vertical scroll yet. Spec behavior:

  • Day opens scrolled to the current time band; swiping to a non-today day keeps the same band (no jump).
  • Scroll position survives view switches — leave Day, come back, same offset.
  • Persist the scroll offset in the shared host layer next to selectedGridDateFlow in CalendarViewModel.kt — that's the seam 5961 built for exactly this, and 5963 needs the same memory for Week/3-Day.
  • Watch the interplay with day/CalendarDayView.kt's HorizontalPager (~20k pages anchored on today): one shared vertical scroll state across pages, not per-page.
4Pull-to-refresh (net-new gesture)Important

FR-23 · AC-17

No PullToRefreshBox exists anywhere in the calendar — Schedule only draws PullToRefreshDefaults.Indicator without the gesture. Build it here; Week/3-Day reuse it.

6Verification sweep — the "already done" FRs + time edgesImportant

FR-5, FR-6, FR-26, FR-15, FR-14, FR-21 · AC-4 AC-5 AC-11 AC-12 AC-20

The prototype implemented these — this ticket owns proving them against the spec, because their ACs are graded here:

  • Overlaps (FR-5): side-by-side shrinking columns, no cap, no overflow affordance — stress with many concurrent events (toEventColumns() first-fit packing).
  • Now-line (FR-6): today only, advances live (60s tick in CalendarCurrentTimeLine).
  • Min height (FR-26): sub-30-min events render at MIN_EVENT_MINUTES = 30.
  • Empty grid (FR-15): no events → empty grid, no message.
  • Device tz + 12/24h (FR-21/14): hour labels + positioning follow device settings.
  • DST-transition day: events position correctly on spring-forward/fall-back days — the classic hour-grid math trap.

Add unit tests around the measurements layer (routing, column packing, min-height, DST) — it's pure logic and the engine 5963 inherits.

Acceptance Criteria for This Ticket — verbatim from the spec

The 10 acceptance criteria this ticket's work is graded against, worded exactly as they appear in the module spec (feature/calendar/spec/viewsspec/spec.md, §Acceptance Criteria). Note its numbering differs from the HTML spec export at the tail (this file's AC-19 = calendar-spec.html's AC-20).

AC-3 (QA #3)Event routing & multi-day edge casesFR-16
  • Given an all-day event (single or multi-day), Then it shows in the all-day row (chip or spanning bar), never on the grid;
  • And given a timed event lasting ≥24h, Then it shows as an all-day-row spanning bar;
  • And given a <24h timed event crossing midnight (e.g. 11pm–1am), Then it renders on the hour grid split into a segment on each day (no all-day bar);
  • And given a single-day timed event, Then it renders on the grid;
  • And given a bar starting before / ending after the window, Then it is clipped to the window edges and breaks at week/period boundaries.
AC-4 (QA #4)Overlap rendering (no cap)FR-5
  • Given a day that has many overlapping timed events, When viewed in Day / 3-Day / Week, Then all overlaps render side-by-side as shrinking columns, with no cap and no overflow affordance.
AC-5 (QA #5)Live now-lineFR-6
  • Given today is visible in Day / 3-Day / Week, When viewing, Then a current-time line is drawn on today's column only;
  • And When time passes, Then the line advances (it is live, not static);
  • And given Month, Then no now-line is drawn.
AC-8 (QA #8)Event tap (phone & tablet)FR-10
  • Given a grid view on a phone, When the user taps an event, Then a full-screen detail opens, and When they back out, Then they return to the same view and date;
  • And on a tablet (list/detail), When the user taps an event, Then the detail pane updates;
  • And on a tablet before any tap, Then the detail pane reflects the focused grid date rather than always today.
AC-11 (QA #11)Localization & timezone (both paths)FR-13, FR-14, FR-21
  • Given the device locale's first day of week is Monday and 24-hour time is on, When viewing Week / Month, Then weeks start Monday and times show 24-hour;
  • And given the default (Sunday first, 12-hour), Then weeks start Sunday and times show 12-hour;
  • And all events render in the device timezone. (3-Day is exempt from week-start — sliding window.)
AC-12 (QA #12)Empty statesFR-15
  • Given a day/week/month with no events, When viewed, Then the empty grid shows with no message;
  • And given Schedule is empty, Then the existing "No events" text shows.
AC-13 (QA #13)Initial scroll & scroll memoryFR-18
  • Given the user opens a time-grid on today, When it appears, Then it is scrolled to the current time;
  • And given a non-today day is opened (via date picker or Month tap), Then it opens at the same time-of-day band;
  • And when the user switches to another view and returns, Then the prior scroll position is preserved.
AC-16 (QA #16)Chip content ("render what fits")FR-22
  • Given an event chip, When rendered, Then the event name always shows and no start/end time shows;
  • And given the chip is tall enough, Then the location fills the remaining space;
  • And given it is too short, Then the location is omitted / truncated with an ellipsis.
AC-17 (QA #17)Refresh behaviorFR-23
  • Given Day / 3-Day / Week / Month, When the user pulls down, Then a calendar sync is triggered and the refresh indicator shows until it completes;
  • And given Schedule, Then no pull-to-refresh gesture exists but its "Refresh" overflow action still triggers a sync. (Month added per PR #1884 review — lands in 5964.)
AC-19 (QA #20)Time-edge casesCodex A13
  • Given a very short (sub-30-minute) single-day timed event, When rendered on the hour grid, Then it shows at the minimum legible height (MIN_EVENT_MINUTES = 30, FR-25);
  • And given a <24h event crossing midnight, Then it renders on the grid split across the two days (not an all-day bar, FR-16);
  • And given a DST-transition day, Then the hour grid and event positions remain correct. (DST behavior provisional — confirm in tech design.)

Note: AC-8's tablet "list/detail + pre-tap seed" wording predates the supporting-pane rework — event detail now opens in a supporting pane only after a tap (no pre-tap seed). The spec + Jira wording are pending update to match.
