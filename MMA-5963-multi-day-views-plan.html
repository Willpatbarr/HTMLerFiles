MMA-5963 — Calendar: Week & 3-Day Views

The Week (7-day) and 3-Day grids, built on the Day rendering engine from 5962. A shared CalendarWeekView already renders both — this ticket fixes the two spec divergences (3-Day paging, week-start locale) and finishes engine adoption.

Type: New Feature Status: New Spec: MMA-5960 (calendar-spec.html) Depends on: MMA-5962 (Day + engine) Sibling: MMA-5964 (Month)

Both views already render on the shared engine — fix the two spec divergences and adopt the rest: rebuild 3-Day paging as a true one-day sliding window with the focused date leading (today it pages in whole 3-day blocks), make Week start on the device locale's first day of week (today it's hardcoded Sunday), thread the shared scroll state + pull-to-refresh in from Day — drill-down is already wired, so everything else is verification.

Remember Only 3 Things

1 — Gap-closing again, not greenfield

week/CalendarWeekView.kt already serves both views (daysToShow = 7 / 3) with pager, nav bar, day headers, all-day row, hour grid. Drill-down to Day is already wired in the host. Don't rebuild.

2 — 3-Day paging is the wrong shape

It pages in whole 3-day blocks (the prototype behavior the spec explicitly calls out as insufficient). FR-20 wants a sliding window: focused date first, advancing one day per step. This is the ticket's real work.

3 — Week-start is hardcoded Sunday

DateUtil.getLastSunday() anchors the week. FR-13 says follow the device locale. Add a locale-aware helper — do not change getLastSunday itself; the callings sustain-date logic depends on its Sunday semantics.

Context Optional

MMA-5961 imported the PMG engine and moved the calendar view layer into :feature:calendar (host + ViewModel stay in app/…/ux/calendar/). MMA-5962 is hardening the shared engine on this branch: routing edge-cases, chips, and — already visible in Day — the host-owned vertical gridScrollState and a PullToRefreshBox. Week/3-Day inherit routing/chips/overlaps/now-line for free because they render through the same grid/ components (CalendarDayColumn, AllDayEventsRow, CalendarGridEventChip).

What they don't inherit automatically: the Day-only seams (scroll state, PTR) still need to be threaded into CalendarWeekView, and two behaviors diverge from spec — 3-Day's block paging and Week's Sunday anchor.

13-Day sliding window — one day per step, focused date leadsMust Know

FR-20 · AC-15

Today's 3-Day is the prototype's rolling blocks: the HorizontalPager in week/CalendarWeekView.kt maps one page per period (periodStartForPage = anchor + (page − ANCHOR) × daysToShow), the nav arrows jump ±daysToShow, and page changes shift the focused date by whole periods to preserve its offset within the window. The spec explicitly flags this: "more work than the prototype's rolling 3-day blocks."

2Week-start follows the device localeMust Know

FR-13 · AC-11

Week anchors on DateUtil.getLastSunday(selectedDate) (week/CalendarWeekView.kt:59) — hardcoded Sunday. Spec: start on the device locale's first day of week (Monday for most of Europe, Sunday for en-US, Saturday for some locales). 3-Day is exempt — it never aligns to weeks.

  • Don't touch getLastSunday — ux/calling/GetEditCallingsUiStateUseCase.kt uses it for sustain dates where "last Sunday" is semantic, not a week-start.
  • Add a locale-aware startOfWeek(date) helper (e.g. in the grid layer next to CalendarConstants), backed by java.time.temporal.WeekFields.of(Locale) — convert at the kotlinx-datetime edge.
  • month/CalendarMonthView.kt:128 has the same Sunday anchor — leave it; 5964 adopts the helper.
  • Unit-test both paths (Monday-first + Sunday-first locales) — AC-11 grades both explicitly.
3Adopt the shared scroll state (open at now + memory)Must Know

FR-18 · AC-13

5962 hoisted a single host-owned gridScrollState (passed into CalendarDayView, day/CalendarDayView.kt:60) so the vertical position is shared across pages and across grid views. CalendarWeekView still creates a rememberScrollState() per pager page (week/CalendarWeekView.kt:116) — so it neither opens at the current time band nor remembers position across view switches.

  • Accept the same scrollState: ScrollState parameter and use it in the verticalScroll — mirroring Day's pattern exactly.
  • Free win: because the state is shared, Day ↔ Week ↔ 3-Day switches keep the same time band automatically (that's the AC-13 cross-view clause).
4Pull-to-refresh in Week / 3-DayImportant

FR-23 · AC-17

5962 built the gesture in Day: PullToRefreshBox at day/CalendarDayView.kt:113, wired to the existing refresh plumbing (workScheduler.refreshCalendar(SyncMode.FULL) + isRefreshingFlow). Week/3-Day have nothing yet.

  • Wrap the pager content the same way Day does — same isRefreshing/onRefresh source, no new plumbing.
  • Gesture must only trigger at the top of the vertical scroll (nested-scroll behavior is standard in PullToRefreshBox, but test mid-scroll pulls on a 7-column grid).
  • Month adopts this same state in 5964 (spec updated per PR #1884 review); Schedule keeps overflow-Refresh only — just don't leak the gesture there.
5Drill-down to Day — verify onlyImportant

FR-11 · AC-9

Already wired: onDayFocused in app/…/ux/calendar/CalendarScreen.kt (~L245) sets the selected date then switches to CalendarViewMode.DAY, and both Week and 3-Day pass it as onDayHeaderClick (headers are clickable in WeekDayHeaderRow).

  • Verify the opened Day lands on the tapped date (not today) and — after WS3 — at the remembered scroll band.
  • Verify view-mode persistence doesn't fight it: setViewMode writes to preferences, so drill-down changes the saved view. Confirm that's the intended UX (it matches how the selector works today).
6Engine-parity verification sweepImportant

FR-5, FR-6, FR-16, FR-22 · AC-4 AC-5 AC-3

The ticket's AC #4 ("engine reuse") is graded here in the multi-day context — Day-view behavior is graded in 5962, but several spec ACs name 3-Day/Week explicitly:

  • Overlaps on narrow columns (AC-4): shrinking side-by-side columns with no cap get very narrow at 1/7 width — stress it; the spec accepts "can get tight" but it must not break.
  • Now-line (AC-5): drawn on today's column only when today is visible in the 3/7-day window — verify it doesn't paint on siblings.
  • Multi-day bars at window edges (AC-3's last clause): a bar starting before / ending after the visible window clips to the edges and breaks at week/period boundaries — only testable in multi-day views, so it's graded here.
  • Chips (FR-22): "render what fits" at 1/7 width — name ellipsizes, no times, location only when it fits.

If 5962's measurement-layer unit tests exist by then, extend them with multi-day window cases (boundary clipping) rather than writing UI tests for pure logic.

AC-11 (QA #11)Localization & timezone (both paths)FR-13, FR-14, FR-21 · WS2 WS6
  • Given the device locale's first day of week is Monday and 24-hour time is on, When viewing Week / Month, Then weeks start Monday and times show 24-hour;
  • And given the default (Sunday first, 12-hour), Then weeks start Sunday and times show 12-hour;
  • And all events render in the device timezone. (3-Day is exempt from week-start — sliding window.)
AC-4 (QA #4)Overlap rendering (no cap)FR-5 · WS6
  • Given a day that has many overlapping timed events, When viewed in Day / 3-Day / Week, Then all overlaps render side-by-side as shrinking columns, with no cap and no overflow affordance. (Day path graded in 5962; the narrow 3/7-column paths are graded here.)
AC-5 (QA #5)Live now-lineFR-6 · WS6
  • Given today is visible in Day / 3-Day / Week, When viewing, Then a current-time line is drawn on today's column only;
  • And When time passes, Then the line advances (it is live, not static);
  • And given Month, Then no now-line is drawn.
AC-3 (QA #3)Event routing & multi-day edge cases — window-boundary clauseFR-16 · WS6
  • …And given a bar starting before / ending after the window, Then it is clipped to the window edges and breaks at week/period boundaries. (The routing rules themselves are 5962's; this boundary-clipping clause is only observable in multi-day windows, so it's graded here.)
AC-13 (QA #13)Initial scroll & scroll memoryFR-18 · WS3
  • Given the user opens a time-grid on today, When it appears, Then it is scrolled to the current time;
  • And given a non-today day is opened (via date picker or Month tap), Then it opens at the same time-of-day band;
  • And when the user switches to another view and returns, Then the prior scroll position is preserved. (Mechanics graded in 5962; Week/3-Day adoption graded here.)
AC-17 (QA #17)Refresh behaviorFR-23 · WS4
