Month View → Custom Layout

MMA-5964 · branch MMA-5964-CustomLayout · plan guide

One-Sentence Version

Replace the month grid's fragile weight-and-Spacer bar alignment with one custom Layout per week row that measures and places cells and bars from a single shared column-edge function.

Must Know

Why — the fragility being removed

Multi-day bars currently span cells via two independent weighted Rows that must agree:

  • The 7 day cells: a Row of weight(1f) children.
  • Each bar lane: a separate Row where bars claim weight(span) and Spacers fill gaps (MonthBarLaneRow, CalendarMonthView.kt:380–407).
  • Vertical bar placement: a hand-maintained padding(top = calendarCellGap/2 + monthDayNumberHeight) contract.

Alignment only holds because both Rows happen to distribute width identically. A custom Layout replaces both with one measured/placed source of truth.

Must Know

The Big Decision — scope: one Layout per week row

Not a whole-grid Layout. Not a bars-only Layout.

Whole-grid Layout — rejected

Weeks are geometrically independent. It would collapse per-week remember(week, eventsByDate, chipCapacity) recomposition scopes and force rework of the verticalScroll/PTR nested-scroll hack — for zero benefit.

Bars-only Layout — rejected

Leaves cells and bars as two width computations that must agree. That is the exact fragility being removed.

Step 1 · Must Know

MonthGrid.kt — two new pure helpers

No behavior change. This is the single source of geometry both cells and bars will use.

/** Left edge of column [col] (0..7). xForCol(7) == totalWidthPx. */
internal fun monthColumnStartX(col: Int, totalWidthPx: Int): Int =
    col * totalWidthPx / DAYS_IN_WEEK

/** Top of bar lane [lane]. Replaces the padding contract. */
internal fun monthBarLaneTop(lane: Int, fontScale: Float): Dp =
    calendarCellGap / 2 + monthDayNumberHeight(fontScale) +
        monthCellLineHeight(fontScale) * lane
  • cellWidth(col) = xForCol(col+1) − xForCol(col)
  • barWidth(a..b) = xForCol(b+1) − xForCol(a)
  • Integer math distributes remainder pixels deterministically — a bar spanning cols a..b meets cell a's left edge and cell b's right edge exactly.
Step 2 · Must Know

New file: MonthWeekLayout.kt

@Composable
internal fun MonthWeekLayout(
    segments: List<MonthBarSegment>,   // pre-filtered: lane < displayedLanes
    modifier: Modifier = Modifier,
    dayCells: @Composable () -> Unit,  // exactly 7, week order
    bars: @Composable () -> Unit,      // one EventBar per segment, same order
)
  • Uses the multi-content-slot overload Layout(contents = listOf(dayCells, bars)) — slot index = role, list index = column/segment. No ParentDataModifier boilerplate (the parent already owns the segment data).
  • Measure (single pass, all Constraints.fixed): cell col → cellWidth(col) × maxHeight; bar i → barWidth(start..end) × lineHeight.roundToPx().
  • Place: cells at placeRelative(xForCol(col), 0); bars at placeRelative(xForCol(startCol), monthBarLaneTop(lane).roundToPx()). placeRelative = RTL mirroring for free.
  • Bars placed after cells → drawn on top (replaces the Box layering). EventBar stays onClick = null so taps fall through — day-cell hit targets remain the full cell.
Must Know

The two steps — what maps to Measure vs Place

A custom Layout's measure policy runs in two passes: measure (how big is each child?) then place (where does it go?). Compose forbids measuring a child twice, so every child gets Constraints.fixed once.

1 · Measure pass (MeasureScope)

Sizes come from column geometry.

Day cell col (7 of them):
Constraints.fixed(cellWidth(col), maxHeight)

Bar i (one per segment):
Constraints.fixed(barWidth(start..end), lineHeight.roundToPx())

Both widths derive from monthColumnStartX(col, constraints.maxWidth) — the shared edge function. The layout's own size is just layout(maxWidth, maxHeight).

2 · Place pass (PlacementScope)

Positions come from column x + lane y.

Day cell col:
placeRelative(xForCol(col), 0)

Bar i:
placeRelative(xForCol(startCol), monthBarLaneTop(lane).roundToPx())

Cells placed first, bars after → bars draw on top (replaces the Box layering). placeRelative mirrors both in RTL.

What each old mechanism becomes

  • Modifier.weight(1f) on the 7 cells → measure: fixed cellWidth(col).
  • Modifier.weight(span) + gap Spacers on bars → measure (bar width) + place (bar x). The Spacers vanish — gaps are just un-placed space.
  • padding(top = calendarCellGap/2 + monthDayNumberHeight) → place: bar y from monthBarLaneTop(lane, fontScale).
  • Box layering (overlay drawn over cells) → place order: bars placed after cells.
  • Row's RTL handling → placeRelative in the place pass.
Not in either pass: chipCapacity / what to compose (chips vs "+N"). That's decided before measure ever runs — at composition time, via BoxWithConstraints. The measure policy only sizes and positions what composition already created.
Step 3 · Important

CalendarMonthView.kt — rewire and delete

MonthWeekRow keeps its remember { monthWeekBarLayout(...) }, then:

val visibleSegments = barLayout.segments
    .filter { it.lane < barLayout.displayedLanes }
MonthWeekLayout(
    segments = visibleSegments,
    modifier = modifier.height(rowHeight).fillMaxWidth(),
    dayCells = { week.forEach { MonthDayCell(...) } },  // drop .weight(1f)
    bars = { visibleSegments.forEach { EventBar(...) } },
)
Required filter: lane < displayedLanes. Today MonthWeekBars drops clipped lanes implicitly by iterating 0 until displayedLanes. Hoist the filtered list once so segments and the bars lambda can't disagree.
Delete: MonthWeekBars, MonthBarLaneRow, the Box+Row layering in MonthWeekRow, the padding(top = ...) contract (its "asymmetric on purpose" comment moves to monthBarLaneTop's kdoc).
Unchanged: MonthDayCell internals — BarSpace spacers stay so chips still slot under bars.
Important

What stays untouched

  • chipCapacity + BoxWithConstraints stay. Capacity decides what to compose (chips vs "+N") — a composition-time decision a Layout can't feed back post-measure. SubcomposeLayout could, but the codebase has none, docs warn on perf, and capacity is uniform (rowHeight = maxHeight/6 everywhere).
  • MonthGrid.kt logic + MonthGridTest.kt — untouched.
  • EventBar.kt — shared with the time grid's AllDayEventsSection; must not change.
  • Pager, PullToRefreshBox, the verticalScroll nested-scroll hack.
  • Optional follow-up WeekdayHeaderRow stays weighted — worst case ≤1px header-vs-grid drift, invisible since labels are centered. Could reuse monthColumnStartX later.
Important

Honest tradeoff

The vertical alignment contract is reduced, not eliminated: cells still consume monthCellLineHeight / monthDayNumberHeight for their line slots while the layout computes bar y from the same helpers.

It shrinks from "two composable trees must agree on padding + weights" to one tested pure function + the existing height helpers. Full elimination would mean layouting every chip as a child of a whole-grid Layout — the overkill option already rejected.

Must Know

Remember Only 3 Things

  1. One Layout per week row — replaces the weighted cell Row + weighted bar-lane Rows + the top-padding contract. Whole-grid and bars-only were both rejected.
  2. monthColumnStartX is the single geometry source — cells and bars both derive edges from it, so alignment is exact by construction, not by coincidence.
  3. Filter lane < displayedLanes before passing segments — the old code dropped clipped lanes implicitly; the new one must do it explicitly.
