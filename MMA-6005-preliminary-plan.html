Agent Gotchas Read First

Dialogs use dialogFlow — no boolean, no composable

The MMA-6004 review commits replaced the old pattern. showRemoveConfirmation: Boolean, the RemoveConfirmed/RemoveDismissed events, and the AlertDialog composable are all gone.

  • Dialogs live on EventDetailsUiState.dialogFlow: StateFlow<DialogUiState<*>?>
  • The ViewModel owns them; the screen already renders them via one existing HandleDialogUiState(uiState.dialogFlow) call
  • So the under-construction placeholder needs no UiState field, no dismiss event, and no composable — just a VM helper

Mirror the existing showRemoveConfirmationDialog():

private fun showUnderConstructionDialog() {
    dialogUiStateFlow.value = MessageDialogUiState(
        text = { stringResource(CoreR.string.feature_under_construction) },
        confirmButtonText = { stringResource(CoreR.string.ok) },
        onConfirm = { dismissDialog() },
        onDismissRequest = { dismissDialog() },
    )
}

dismissDialog() already exists. No title, no dismiss button — it is informational, not a confirmation.

There is no loading flag any more

A later MMA-6004 commit (de7b880bb3, "Share Event Details state with stateInDefault") deleted EventDetailsUiState.loading. The state is now nullable end to end:

  • uiStateFlow: StateFlow<EventDetailsUiState?>, seeded null via stateInDefault
  • null = not loaded yet. notFound still means the event genuinely does not exist locally
  • The screen composable and menuItems() both take EventDetailsUiState?

Anywhere this guide or your muscle memory says loading = true — in a preview state, a screen test, or a UiState copy — write uiState = null instead. loading = false just disappears; it is not replaced by anything.

menuItems() changed shape

It is no longer an expression-bodied buildList — it takes a nullable EventDetailsUiState? and early-returns emptyList() when uiState == null || uiState.notFound, with the buildList inside. Add the QR icon and Duplicate item inside that buildList. Two screen tests pin the null/not-found empty behavior; don't break them.

Two similarly-named booleans — pick the right one

  • EventDetails.isPublic — is this event public. This is the one every gate in this ticket wants.
  • EventDetailsCalendar.isPublicEventsEnabled — whether this calendar is allowed to create public events. A capability flag, unused by the details screen. Never use it for these gates.

Grepping for "public" hits both. Wiring the calendar flag compiles, and on sample data where public events sit on public-capable calendars the tests can still pass — so this mistake hides. Both live in repo/calendar/…/EventDetails.kt.

String keys — feature-local, not core

Add these to feature/calendar/src/main/res/values/strings.xml alongside the existing calendar_event_* family (with comment attributes, matching siblings):

  • calendar_event_duplicate — "Duplicate Event" (overflow item)
  • calendar_event_qr_code — QR app-bar action content description
  • calendar_event_rsvp — RSVP FAB content description
  • calendar_event_photo — hero image content description

Reuse, do not re-declare: calendar_event_audience ("Audience", feature-local) and view_calendar_event_link / view_calendar_event_caption / feature_under_construction (all core:strings).

Verified assumptions — no substitution needed

  • Icons.Rounded.QrCode and Icons.Rounded.Rsvp both exist in material-icons-extended 1.7.8, already a :feature:calendar dependency
  • AudienceGroup and EventAudience.labelRes both live in the edit package, same module — import across packages is fine
  • ok and feature_under_construction both exist in core:strings
  • No new constructor params in your changes, so Koin wiring is untouched — but note a CalendarIntents class now exists in a new intent/ package and is registered in the feature module; the ViewModel injects it alongside calendarExternalIntents
