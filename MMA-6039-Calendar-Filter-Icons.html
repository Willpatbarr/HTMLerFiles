MMA-6039 — Calendar: Update Filter Icons

Give the visibility sheet and the subscriptions screen distinct icon languages, and group both lists into sections.

Type: Enhancement Parent: LTS-2600 Status: In Progress Branch: MMA-6039 Base: 0b616e604c
One-sentence version: Two calendar screens looked identical but did different things, so the sheet now uses eye / eye-off icons, the subscriptions screen uses real switches, and both lists group by CalendarType — three commits, all gates green, not yet pushed.
Must Know

Remember Only 3 Things

  1. Visibility ≠ subscription. The sheet hides a calendar you already subscribe to (local displayed flag). The screen controls whether you receive it at all (server-side saveSubscriptions()). They used the same checkbox affordance — that was the bug.
  2. Sections come from data that already existed. CalendarType is declared HEAD_QUARTERS, BUILDING, UNIT — exactly the design's section order. No new data, no new sorting.
  3. Nobody wrote acceptance criteria for this ticket. Jira is one line with zero comments. The AC below were derived after the fact from the mock, the decisions, and the tests — get them agreed before review.
Must Know

The Design Problem

The ticket body was one line: "update the icons for the visibility filter popup and the manage subscriptions." The real problem sits underneath that.

Two screens control what a user sees on the calendar, and they looked nearly the same while doing genuinely different things:

Visibility sheet

A bottom sheet, "Show or Hide Calendars"

Flips a local Calendar.displayed flag on calendars you already subscribe to. Reversible, instant, private to your device.

feature/calendar/…/schedule/ScheduleView.kt

Subscriptions screen

A full screen, was "Manage Calendars"

Flips server-side subscription via saveSubscriptions(). Has a save button, a discard-changes dialog, and network consequences.

app/…/ux/calendar/manage/ManageCalendarsScreen.kt

Both rendered a checkbox-shaped control on the left of each row. Nothing on screen told you which kind of action you were about to take.

The grouping was already possible

The mock's three sections map exactly onto the existing CalendarType enum:

enum class CalendarType {
    HEAD_QUARTERS, BUILDING, UNIT;   // Church Headquarters / Locations / Calendars
}

Because the enum is declared in display order, CalendarType.entries gives the section order for free — no ordering constant, no sort comparator.

Acceptance Criteria

These are derived, not given

Jira MMA-6039 has a one-line description and zero comments. No FRs, no AC. The nearby feature/calendar/spec/viewsspec/spec.md does carry FR-1…FR-26 / AC-1…AC-20, but that covers the calendar views work — the closest overlap is FR-7 / FR-8 / FR-17 on the shared displayed flag, and none of it mentions icons or grouping. That spec folder is also owned by someone else.

The list below was reconstructed from the mock, the locked decisions, and the eight tests. Get it agreed before review — otherwise reviewers are judging against a screenshot.

Grouping — both screens

  1. Calendars are grouped into sections rendered in the order Church Headquarters → Locations → Calendars, regardless of the order the query returns them.
  2. A calendar type the user has no calendars for renders no header — no empty sections.
  3. Order of calendars within a section is unchanged from the repository query.
  4. A user with no calendars at all sees no headers and no rows.

Visibility sheet

  1. Each row shows an eye icon in the trailing position: open eye when shown, crossed-out eye when hidden.
  2. Tapping a row toggles only that calendar, flips its icon, and adds or removes its events from every calendar view.
  3. The visibility state persists across app restarts and is unchanged by this ticket in mechanism (still the repository displayed flag).
  4. The sheet keeps its title "Show or Hide Calendars" and its header ✓ dismiss action.

Subscriptions screen

  1. The screen is titled "Calendar subscriptions".
  2. Each row shows a real Switch in the leading position; the calendar-color palette stays trailing.
  3. A calendar the user cannot unsubscribe from shows the switch on and disabled, and the row does not respond to taps.
  4. Toggling then confirming with ✓ persists the change; reopening the screen shows the new state.
  5. Leaving with unsaved changes still raises the discard-changes dialog.
  6. Subscribing to a new calendar makes it appear in the visibility sheet, in the correct section.

Accessibility

  1. Each row is a single TalkBack focus target announcing the calendar name and its state — no separate stop for the eye or the switch.
  2. The subscriptions row announces a switch role (it previously announced no role at all).

Explicitly out of scope

The mock renders each section as a grey filled card (the SettingsScreen treatment — label floating above a filled Card). Flat headers shipped instead. This is the one open design question.

Important

Codebase Convention Audit

The first draft of the plan was audited against the codebase before any code was written. It broke three conventions and missed one existing file.

Three breaks, fixed before implementing

  1. groupBy in the composable. 20 of 21 groupBy call sites in the app live in use cases. Moved.
  2. Ad-hoc section iteration in the UI. The house pattern is a sealed UiModel with a Header variant, built in the use case — DirectoryUiModel, CovenantPathPerson, ProxySearchUiModel. ScheduleUiModel in the very same file already did it.
  3. File named CalendarSection.kt. Extension files are *Ext.kt here — 39 such files exist and 25 hold exactly one declaration, so a small single-purpose file is the norm, not an exception. OrdinanceTypeExt.kt is a near-exact template.

One miss

app/src/test/…/grid/GetCalendarGridUiStateUseCaseTest.kt already existed and covers the use case being changed. It became the home for the sheet's sectioning tests instead of a new file.

Optional

Confirmed already-conventional

  • Icons.Rounded.Visibility / VisibilityOff — precedent in SyncOptionsScreen, HomeUiModel
  • Switch(onCheckedChange = null) + role = Role.Switch — SettingSwitchRow
  • @param:StringRes on header ids, TextHeader(color = Color.Transparent), contentType = "Header"
  • material-icons-extended already on both modules — no new drawables, no Gradle change
Must Know

Locked Decisions

1. Flat TextHeader sections, no cards

Matches every other sectioned list in the app and keeps the subscriptions LazyColumn's per-row keys. Diverges from the mock. Still open with Jared.

2. Plain item, not stickyHeader

Both appear here (25 sticky vs ~39 plain), and plain is the more recent pattern — Settings sections, Birthday list. Sticky also still needs @OptIn(ExperimentalFoundationApi::class). Three short sections gain nothing from pinning.

3. Reuse R.string.calendars for the UNIT section

Avoids a third string with identical English. That string is used in exactly two places — one is the filter chip that opens this very sheet — and its "Status of Calendars" comment is stale. Only two new strings added.

4. Title stays sentence case

The existing calendar_subscriptions string reads "Calendar subscriptions" and was previously unused. No runtime title-casing: title case is an English convention and would mangle roughly 30 sentence-case locales.

5. Switch sits leading, not trailing

Every Switch precedent in the app is a single-control row. This row has two controls and already put one leading with the palette trailing. Moving the switch trailing would force the interactive palette to leading: more churn, worse accessibility. A code comment records this.

6. Palette stays hidden on unsubscribed rows

Pre-existing behavior (if (isVisibleOnAgenda)), carried forward unchanged. The mock appears to show a palette on every row regardless of toggle state. Kept as-is: you cannot meaningfully pick a color for a calendar you do not receive, and changing it is outside an icons ticket. Flag to Jared rather than change silently.

7. Unit-name subtitle stays

The mock has no subtitle; the build shows the unit under each calendar name. Redundant for a single-unit user, but essential when a stake user sees same-named calendars from several units at once. Kept.

Accessibility note worth preserving

MMA-6010 (commit 5d8ec3201a) deliberately replaced eye-like glyphs with a real Checkbox after review flagged missing semantics. This change goes back to a glyph — but keeps toggleable(role = Role.Checkbox) on the row and makes the eye decorative, so TalkBack still announces state with one focus target. Lead the PR description with this so the same comment doesn't recur.

One deviation from the approved plan

The plan put manage-screen grouping inside the use case. The preview provider needs the same logic, so toSectionedCalendars() became a shared top-level function beside the model, called by both.

Known duplication a reviewer may raise: toSectionedDisplayCalendars() and toSectionedCalendars() are the same ~8-line algorithm over different types. A generic version would need three lambdas — judged less readable than the duplication.

Resolved

Build Blocker — Resolved

Expired JFrog token, surfaced by a Gradle bump

Fixed by rotating the Artifactory identity token. Recorded here because it will recur.

Three facts combined:

  1. The rebased base upgraded Gradle 9.6.1 → 9.7.0, which needs kotlin-dsl plugin 6.7.3
  2. Only 5.1.2 and 5.2.0 were cached, so that artifact had to hit the network — the first one in a long while
  3. The Artifactory identity token had silently expired, so jfrog returned 401

Teammates hit the same thing the same week; the fix in every case was generating a new token at icseng.jfrog.io/artifactory and updating icsJfrogPassword in ~/.gradle/gradle.properties.

Two misleading symptoms

  • Android Studio reported "The settings are not yet available for build ':'" — an IllegalStateException during init-script processing, with no 401 anywhere in idea.log. It was the same expired token; the nested build-logic build failed to evaluate and Gradle reported it unhelpfully.
  • A warm cache hid it for weeks. The token was probably dead long before anything broke.
Optional

Interim workaround used before the fix

Verification initially ran with composeRichEditor pinned back to the cached 1.0.0-rc14 and --offline. That pin never entered a commit. It is no longer needed — the gates now run against the real dependency set.

The check that can silently prove nothing

If your unit only has UNIT-type calendars you will see a single "Calendars" header and no grouping. That is correct behavior (AC-2), but it means AC-1 went untested. Use a proxy unit with building or headquarters calendars to actually exercise the ordering.
