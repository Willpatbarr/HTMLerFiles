Why This Change Must Know

Two goals, and they're the only two:

  1. Make the structure intuitive and less cluttered. Five tickets of calendar work grew the module one package at a time, so the root accumulated 17 flat packages — six of them (day/, week/, threeday/, month/, schedule/, grid/) are all the same concern: how a calendar is rendered. Nothing at the root said so. They now sit under one views/ parent, so "where does the week view live" has an obvious answer.
  2. Make genuinely common things common. Several things every view mode uses were filed as if they belonged to one of them:
    • CalendarConstants.kt — its own doc says "shared across the calendar views," yet it sat inside grid/ like an engine internal. DAYS_IN_WEEK/MONTHS_IN_YEAR are used only by month, week, and the app's sample data.
    • CalendarDateNavBar, CalendarViewMode, CalendarViewModeSelector — chrome that frames every view mode, also buried in grid/.
    • The Calendars filter sheet serves all five view modes, but lived inside ScheduleView.kt / ScheduleUiState.kt — one view mode's files owning shared scaffolding.

That mis-filing had a concrete cost: a bidirectional dependency. grid/CalendarsFilterUiState.kt imported schedule.DisplayCalendarsUiState while schedule/ScheduleView.kt imported grid.CalendarGridDefaults — the two packages pointed at each other purely because the shared sheet was stored in the wrong place.

Not a goal: deleting one-file packages. day/, week/ and threeday/ keep their own folders under views/, and nav/ is left alone entirely. Small folders are fine; badly-placed shared code is not.

The end state is a one-way graph: views/grid → views (constants), views/grid → views/filter, views/schedule → views/grid, and views/filter depending on nothing inside views/. No behavior changes — the app must look and act identically after.

Why grid/ stays one folder Changed

The earlier draft added a views/grid/layout/ sub-folder for "pure math, zero Compose." Checked against the files — that rationale is false for half of them:

  • CalendarGridSnap.kt imports androidx.compose.foundation.pager.PagerSnapDistance.
  • CalendarGridZoom.kt declares Modifier.calendarPinchToZoom using pointerInput and the gesture APIs. That is not math.
  • Worse, the split is cyclic: AllDayLanes.kt and CalendarEventColumns.kt both operate on CalendarGridEvent, which lives in grid/CalendarGridUiState.kt — so layout/ would import grid/ while grid/ imports layout/. That's the same smell ride-along 3 exists to remove.

Making it acyclic means moving CalendarGridEvent down into layout/ — which breaks a real convention. In this codebase a XxxUiState.kt holds its whole state family, item models included: SettingsUiState.kt 9 declarations, ProfileImagePreviewUiState.kt 7, AutoUpdateUiState.kt / ActionInterviewUiState.kt / SyncOptionsUiState.kt 5 each. It would be the only case in the repo of a UiState importing its own item model from another package.

AlsoA layout/ split would be a structural line drawn on a rule that is not actually true of its contents — the opposite of making the tree intuitive.
And13 files matches recurrence/ exactly, and sits under edit/'s 22. A normal folder for this module, not an outlier.

If grid/ grows past ~18 again, splitting it is a clean standalone ticket. Note the filter extraction does not break the UiState convention: ScheduleUiState holds no display-calendars state, so DisplayCalendarsUiState.kt lands in filter/ as a complete, self-contained family with no import back.

What does move out of grid/, and why

  • Chrome — CalendarDateNavBar, CalendarViewMode, CalendarViewModeSelector are not the engine; they frame every view mode. They go to the views root.
  • CalendarConstants.kt was never grid-internal — its own doc says "shared across the calendar views," and DAYS_IN_WEEK/MONTHS_IN_YEAR are used only by month/, week/, and the app's sample data. Views root.
  • CalendarsFilterUiState.kt → views/filter/, which is what kills the backwards import.
  • Everything else stays. EventBar.kt and AllDayLanes.kt are reached into by month/, and only CalendarGridSnap.kt is truly grid-private — grid/ was never a black box, and pretending otherwise with sub-folders just misnames things.
