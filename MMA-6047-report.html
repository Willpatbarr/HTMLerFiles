MMA-6047 — What's New sheet stuck at Hidden

The sheet is not gone. It is still composed, parked at its Hidden anchor, behind a transparent full-screen scrim that still takes every tap.

│ What the reporter saw

Reproduction

  1. Sign in with a proxy user; dismiss What's New if shown.
  2. Settings → Account → Clear Data → OK.
  3. Re-enter the same proxy username, Sync, set the PIN.
  4. When What's New appears over Home, dismiss it by dragging it down, promptly, possibly while the sheet is still settling.
  5. Tap anything.

Pixel 9 emulator, API 36, debug build, proxied as Harbor Ward BISHOP. Reproduced repeatedly under instrumentation, including on 16c5e2d7bb.

Every input is swallowed, and the app looks healthy

Home renders normally. No sheet is on screen. Taps on the Home edit button, the tiles, the bottom bar and the scrim itself all do nothing, and the hardware back button does nothing. Only killing the process recovers.

An app that looks fine and ignores all input is indistinguishable from a hang.

The reporter's own hypothesis was right, and this document narrows it

The ticket guesses "the composable that hosts the sheet believes it is already dismissed (so onDismissRequest no-ops) while the sheet was never removed from composition." The Material 3 sources confirm the second half exactly, and invert the first: the composable believes the sheet is still showing, while the sheet believes it is Hidden.

│ What the invisible view actually is

Not a leaked window. A live, correct ModalBottomSheet in a state the app never checks for.

Every quoted block below is from androidx.compose.material3:material3-android:1.5.0-alpha27, the version pinned at gradle/libs.versions.toml:66. Nothing here is Material 3 misbehaving — it is Material 3 doing precisely what it says it does, with a SheetValue the app has no opinion about.

1 · The scrim's tap handling does not depend on its alpha

material3/commonMain/.../Scrim.kt:50-77

alpha reaches only drawRect; pointerInput and semantics are unconditional

kotlin
public @Composable fun Scrim(contentDescription: String?, ..., alpha: () -> Float) {
    ...
    val dismissModifier = if (dismissEnabled) {
        Modifier.pointerInput(onClick) { detectTapGestures { onClick() } }   // no alpha here
            .semantics(mergeDescendants = true) { this.contentDescription = ... }
    } else Modifier
    Canvas(modifier = modifier.fillMaxSize().then(dismissModifier)) {
        drawRect(color = color, alpha = alpha().coerceIn(0f, 1f))          // only here
    }
}
  • Consequence: at alpha 0 the scrim is a full-screen, fully clickable, accessibility-visible node that draws nothing.
  • Consequence: that is the node in the window dump, character for character.

The terminal state, stated once

whatsNewItems != null and sheetState.currentValue == Hidden at the same time.

Composition says showing. The sheet says gone. Nothing in the app reconciles the two, and the only bridge between them runs in one direction.

│ The two sources of truth, and the one edge between them

The shape of the defect

HelpViewModel SheetState ────────────── ────────────── showBottomSheetStateFlow currentValue │ │ │ null / non-null decides │ Hidden / Expanded decides │ whether the composable exists │ where the sheet is drawn ▼ ▼ composed ──────────────────────────▶ shown composed ◀────── onDismissRequest ── Hidden ← the only edge back composed (nothing) Hidden ← when that edge is missed

The forward direction is structural — a non-null list composes the sheet. The return direction is a single callback fired from the completion of a coroutine inside Material 3. Miss it once and the two never re-synchronise.

Source of truth one — the ViewModel flag

app/.../ux/help/HelpViewModel.kt:55-69

a non-null list is the entire instruction to show the sheet

kotlin
val showBottomSheetFlow: StateFlow<List<WhatsNewItem>?> = combine(
    showBottomSheetStateFlow, settingsRepository.getVisibilityOnboardingCompletionDateFlow(),
    permissionsFlow, whatNewBottomSheetHasShownFlow,
) { ... }.mapLatest { (showBottomSheet, visibilityOnboardingCompletionDate, ...) ->
    if (showBottomSheet && !SecurityManager.isSessionExpired() && (... != null || ...)) {
        whatNewBottomSheetHasShownFlow.value = true      // writes to its own upstream
        getWhatsNewItems(permissions)
    } else {
        null
    }
}.stateInDefault(viewModelScope, null)
  • Note: the flow knows nothing about SheetValue. It cannot tell a showing sheet from a Hidden one.
  • Note: whatNewBottomSheetHasShownFlow.value = true is a write from inside mapLatest into that same combine's upstream, which cancels and restarts the block it is written in.

Source of truth two — the sheet position

app/.../ux/help/HelpScreen.kt:80-98

state remembered above the if, so it outlives every show and dismiss

kotlin
@Composable
fun WhatsNewBottomSheet(showBottomSheetFlow: StateFlow<List<WhatsNewItem>?>, dismissBottomSheet: () -> Unit) {
    val whatsNewItems = showBottomSheetFlow.collectAsStateWithLifecycle().value
    val bottomSheetState = rememberBottomSheetState(
        initialValue = SheetValue.Hidden, enabledValues = setOf(SheetValue.Hidden, SheetValue.Expanded))

    if (whatsNewItems != null) {
        ModalBottomSheet(sheetState = bottomSheetState, onDismissRequest = { dismissBottomSheet() }, ...) {
            WhatsNewList(whatsNewItems, ...)
        }
    }
}
  • Note: rememberBottomSheetState is rememberSaveable-backed and saves currentValue — the position survives the dismiss, and survives process death.
  • Note: dropping PartiallyExpanded from enabledValues means hasPartiallyExpandedState is false, so every settle path goes straight to hide().

The bridge, and what it costs to miss

app/.../ux/help/HelpViewModel.kt:81-84

the only thing that ever un-composes the sheet

kotlin

    tipsUtil.tipsShownAsync()
}
  • Reached from: onDismissRequest only — nothing else in the app clears the flag.
  • Fired by: three Material 3 call sites, every one of them the completion handler of a coroutine, listed under Three Dead Exits.

The sheet is hosted over every screen in the app

app/.../ux/main/MainActivity.kt:146-149

  • Consequence: the scrim covers Home, the drawer, the bottom bar and every destination inside Nav3Host.
A second, independent host exists

HelpScreen.Content composes its own WhatsNewBottomSheet at HelpScreen.kt:65-68, driven by a different HelpViewModel instance — MainActivity takes one by viewModel(), the Help nav entry takes another by koinViewModel() (nav3/di/Nav3HelpKoinModule.kt:46).

Two hosts, two flags, one shared sheet concept. This is not the reported repro path, which happens on Home, but it is the same defect class and it is worth deciding about while the fix is being designed.

│ Why nothing the user does recovers it

All three exits are gated on the same invariant the state has already broken

Each one asks, in its own way, "is the sheet visible?" — and at Hidden the honest answer is no, so each one declines to act. The state that needs dismissing is the one state in which nothing will dismiss it.

Exit 1 · The hardware back button is switched off at Hidden

material3/commonMain/.../BottomSheet.kt:157, SheetDefaults.kt:215-216

enabled is false exactly when the sheet is already Hidden

kotlin
// BottomSheet.kt
PredictiveBackHandler(enabled = backHandlerEnabled && state.isVisible) { progress -> ... }

// SheetDefaults.kt
public val isVisible: Boolean
    get() = anchoredDraggableState.currentValue != Hidden
  • Result: no back handler is registered, and the dialog window still holds focus, so the press reaches nothing. Matches "repeated back-presses all failed".

Exit 2 · Tapping the scrim asks a mutex that a stalled drag may still hold

material3/commonMain/.../ModalBottomSheet.kt:113-123

hide() is a mutation on the same anchored-draggable state the drag owns

kotlin
val animateToDismiss: () -> Unit = {
    if (sheetState.confirmValueChange(Hidden)) {
        scope.launch { sheetState.hide() }
            .invokeOnCompletion { if (!sheetState.isVisible) { onDismissRequest() } }
    }
}
  • If the drag coroutine completed: this works, and the scrim tap would have recovered the app. It did not, in any observed reproduction.
  • If it did not: hide() is a lower-priority mutation than a user-input drag, so it waits behind it and invokeOnCompletion never runs.

Exit 3 · The settle callback only fires if its coroutine finishes

material3/commonMain/.../BottomSheet.kt:249-256

the dismiss for a drag lives in a finally inside performFling

kotlin
override suspend fun ScrollScope.performFling(initialVelocity: Float): Float {
    ...
    var remainingVelocity = 0f
    try {
        remainingVelocity = with(anchoredDraggableFlingBehavior) { performFling(safeVelocity) }
    } finally {
        if (!state.isVisible) onDismissRequest()          // the whole dismiss, for a drag
    }
    return remainingVelocity
}
  • Result: a drag that settles to Hidden without this coroutine reaching its finally leaves the flag set and the composable alive. There is no later re-check.

The app adds no fourth exit

Possible recoveryPresent?Why not
A LaunchedEffect watching currentValue == Hidden No WhatsNewBottomSheet has no effect of any kind
Clearing the flag when the sheet leaves the screen No Nothing observes bottomSheetState at all
Resetting the flag on re-entry to Home or Ready No enterReadyState is one-shot, guarded by readyEntered
Snapping the state back to Expanded on a stale show No rememberBottomSheetState is hoisted and never reset

Candidates for the trigger, none yet isolated

#CandidateWhy it fits
1 A drag begun while the opening show() animation is still running Matches the repro wording exactly. Two mutations contend for the same anchored-draggable state, and the loser's finally is the dismiss.
2 The sheet leaving and re-entering composition mid-gesture as hostStateFlow reseeds during re-login Clear-data re-login drives Download → PIN → Home, each reseeding hostState, and state.ready gates the sheet's composition.
3 Fallout from the pool-closed crash, MMA-6046 The reporter notes MMA-6046 had fired earlier in every observed reproduction. The ticket itself asks for both together and in isolation.
The fix should not depend on identifying the trigger

All three candidates end in the same place, and so would a fourth nobody has thought of: the sheet reaches Hidden and the flag stays set. A fix that reconciles the two sources of truth closes every one of them at once; a fix that chases one race closes one.

Open questions for the fix

  1. Should the second host in HelpScreen.Content stay, given MainActivity already renders the sheet over every destination?
  2. Does MMA-6046 need to be fixed or excluded first, or is this independent of it?
  3. Should whatNewBottomSheetHasShownFlow.value = true move out of mapLatest, or is that a separate ticket?
