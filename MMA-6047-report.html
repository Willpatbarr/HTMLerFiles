MMA-6047 — What's New sheet stuck at Hidden

The sheet is not gone. It is still composed, parked at its Hidden anchor, behind a transparent full-screen scrim that still takes every tap.

│ What the reporter saw

Reproduction

  1. Sign in with a proxy user; dismiss What's New if shown.
  2. Settings → Account → Clear Data → OK.
  3. Re-enter the same proxy username, Sync, set the PIN.
  4. When What's New appears over Home, dismiss it by dragging it down, promptly, possibly while the sheet is still settling.
  5. Tap anything.

Pixel 9 emulator, API 36, debug build, proxied as Harbor Ward BISHOP. Reproduced repeatedly under instrumentation, including on 16c5e2d7bb.

Every input is swallowed, and the app looks healthy

Home renders normally. No sheet is on screen. Taps on the Home edit button, the tiles, the bottom bar and the scrim itself all do nothing, and the hardware back button does nothing. Only killing the process recovers.

An app that looks fine and ignores all input is indistinguishable from a hang.

The reporter's own hypothesis was right, and this document narrows it

The ticket guesses "the composable that hosts the sheet believes it is already dismissed (so onDismissRequest no-ops) while the sheet was never removed from composition." The Material 3 sources confirm the second half exactly, and invert the first: the composable believes the sheet is still showing, while the sheet believes it is Hidden.

│ What the invisible view actually is

Not a leaked window. A live, correct ModalBottomSheet in a state the app never checks for.

Every quoted block below is from androidx.compose.material3:material3-android:1.5.0-alpha27, the version pinned at gradle/libs.versions.toml:66. Nothing here is Material 3 misbehaving — it is Material 3 doing precisely what it says it does, with a SheetValue the app has no opinion about.

│ The two sources of truth, and the one edge between them

The shape of the defect

HelpViewModel SheetState ────────────── ────────────── showBottomSheetStateFlow currentValue │ │ │ null / non-null decides │ Hidden / Expanded decides │ whether the composable exists │ where the sheet is drawn ▼ ▼ composed ──────────────────────────▶ shown composed ◀────── onDismissRequest ── Hidden ← the only edge back composed (nothing) Hidden ← when that edge is missed

The forward direction is structural — a non-null list composes the sheet. The return direction is a single callback fired from the completion of a coroutine inside Material 3. Miss it once and the two never re-synchronise.

│ Why nothing the user does recovers it

All three exits are gated on the same invariant the state has already broken

Each one asks, in its own way, "is the sheet visible?" — and at Hidden the honest answer is no, so each one declines to act. The state that needs dismissing is the one state in which nothing will dismiss it.

Proposed fix — the position is the dismissal

Stop trusting one callback to report a dismissal. Watch where the sheet actually is, and treat reaching Hidden as the dismissal however it got there.

│ One sentence, then two pictures

The sheet already knows it is gone. Nobody asks it.

Today the app learns about a dismissal by being told, through onDismissRequest. The fix is to stop waiting to be told and look instead — the sheet's own SheetValue is public, always correct, and reaching Hidden means exactly one thing.

Today — one edge, and it can be missed

flag = true ──▶ sheet composed ──▶ show() ──▶ Expanded │ drag down ▼ flag = false ◀── onDismissRequest ◀── Hidden the happy path flag = TRUE ◀── (nothing) ◀── Hidden MMA-6047 │ └─▶ still composed · alpha 0 · eats every tap · forever

Nothing re-checks. The two halves disagree from that moment until the process dies.

After — a second edge that cannot be missed

flag = true ──▶ sheet composed ──▶ show() ──▶ Expanded │ drag down ▼ flag = false ◀── onDismissRequest ◀── Hidden still the fast path flag = false ◀── watcher sees it ◀── Hidden the backstop

The watcher does not replace onDismissRequest — it runs beside it. Whichever notices first clears the flag; the second finds nothing left to do.

What actually changes

TodayAfter
Decides the sheet is gone A callback fired from a coroutine's completion The sheet's own settled position
Fails when That coroutine is interrupted, cancelled, or stalls The sheet never reaches Hidden at all — in which case it is still on screen and still usable
Worst case The whole app is frozen until it is force-killed A dismissal is recorded a frame or two later than it might have been

Why not chase the race instead

Three candidate triggers were listed on the Issue page and none has been isolated. All three land in the same terminal state, and so would a fourth nobody has found yet. Watching the position closes every one of them at once without needing to name any of them.

It is also the smaller change: two edits in one file, plus a test.

The assumption this fix rests on, stated plainly

It assumes SheetState.currentValue does reach Hidden in the stuck state. The window dump proves the offset reached the Hidden anchor — the scrim had faded and the sheet had left the screen — so the settle animation completed and currentValue should have followed it.

To falsify: reproduce with a logging snapshotFlow on currentValue and confirm it reads Hidden while the app is frozen. If it reads Expanded, the watcher must move to SheetState.isVisible instead and the arming rule changes with it.

1.1 — Add DismissWhenHidden Composable

app/.../ux/help/HelpScreen.kt

arms once the sheet has been on screen, then fires on the return to Hidden

kotlin
@OptIn(ExperimentalMaterial3Api::class)
@Composable
internal fun DismissWhenHidden(sheetState: SheetState, onHidden: () -> Unit) {
    LaunchedEffect(sheetState) {
        // Hidden is also the initial value, so arm only once the sheet has been shown.
        snapshotFlow { sheetState.currentValue }.first { it != SheetValue.Hidden }
        snapshotFlow { sheetState.currentValue }.first { it == SheetValue.Hidden }
        onHidden()
    }
}
  • Why:
  • B — MMA-6047: a dismissal that never reports itself freezes the whole app
  • C — onDismissRequest is the only edge back, and all three of its call sites are coroutine completion handlers

│ Deliberately left out

Four things this fix does not touch, and why

Each is real. None of them is the defect, and folding any of them in would make a two-edit bug fix into something a reviewer has to take on faith.

The duplicate host in HelpScreen

HelpScreen.Content composes its own WhatsNewBottomSheet from a second HelpViewModel instance. Removing it means unifying the flag into a shared holder, because the Help menu item writes to the Help copy's flow.

Left out because the Step 1 watcher lives inside WhatsNewBottomSheet, so both hosts are protected either way. Worth a follow-up ticket, not this one.

The write inside mapLatest

whatNewBottomSheetHasShownFlow.value = true is written from inside mapLatest into that same combine's own upstream, which cancels and restarts the block it sits in.

Left out because it is a real smell with no demonstrated link to the freeze, and changing when the sheet is eligible to appear is a behaviour change riding along on a bug fix.

MMA-6046, the pool-closed crash

The reporter notes MMA-6046 had fired earlier in every observed reproduction and asks for both together and in isolation.

Left out because the fix does not depend on the answer. If MMA-6046 is the trigger, the watcher still clears the flag; if it is not, nothing changes.

A timeout for "never opened"

If show() were cancelled before the sheet moved at all, the watcher would never arm. A bounded wait would cover it.

Left out because a timeout trades a rare stuck state for a routine flaky one on slow devices, and Step 2 makes the case much harder to reach by guaranteeing a fresh state at every show.

│ Plan against reality

What the plan got right and did not have to revisit

  • The two sequential first calls close the gap they were meant to — snapshotFlow re-emits the current value on collection, so a flip to Hidden between them is caught by the second one's first emission.
  • show() and hide() with no sheet laid out do update currentValue, as SheetDefaults.kt:307-319 documents. The test harness depends on this and it held.
  • The effect ends after one onHidden(), so the callback cannot fire twice while the flag write makes its way back through combine and mapLatest.
  • Konsist raised nothing. ComposeTest only requires a default on a modifier parameter, and DismissWhenHidden has none.
Unrelated, and caught on the way past

The build regenerated three untracked schema JSON files — member/49, calendar/9 and map/2. They are in-flux versions and domain-context.md says not to commit them, so they were unstaged and left on disk.

Worth knowing because git add -A in this worktree will pick all three up.

│ P1 — the watcher can fail to arm Blocking

Two independent paths, one of them the ticket's reproduction

The arming line waits for currentValue to leave Hidden. If it never does, the watcher never arms, the later drag to Hidden is missed, and MMA-6047 recurs with a fully green suite.

Path A — the open animation is interrupted

SheetState.currentValue is anchoredDraggableState.settledValue (SheetDefaults.kt:198-202), and settledValue is assigned after the cancellable section of anchoredDrag. Grab the sheet mid-open and the open never settles, so settledValue never leaves Hidden.

MMA-6047's reproduction step 4, verbatim: "dismiss it by dragging it down (a prompt drag, possibly while the sheet is still settling)." That is this path.

Path B — snapshotFlow conflates

capacity-1 channel plus a distinct-until-changed guard, from the runtime source

kotlin
val needToRerunBlock = Channel<Unit>(1)
var lastValue = manager.runAndWatch(needToRerunBlock, block)
emit(lastValue)
while (true) {
    needToRerunBlock.receive()
    val newValue = manager.runAndWatch(needToRerunBlock, block)
    if (newValue != lastValue) { lastValue = newValue; emit(newValue) }
}
  • Consequence: a Hidden → Expanded → Hidden round trip completed before the collector resumes re-reads Hidden, equals lastValue, and emits nothing. AOSP's own KDoc: "State change events are conflated."
  • Reachable via: updateAnchors snapping settledValue during layout (BottomSheet.kt:310-326), so two layout passes in one frame can produce a round trip the collector never sees.
