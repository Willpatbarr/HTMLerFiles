ManageCalendarsScreen is the block shown. DisplayCalendarsSheet and DirectoryListScreen carry the same two lines against their own receiver — model and person — and the sheet chains them after an existing fillMaxWidth().

Why the change was needed

Three screens gained segmented rows across MMA-5381, MMA-6039 and MMA-6040, and none of them set a gutter or a gap between sections. Blocks ran edge to edge and adjacent sections read as one block.

What the change does

Insets every row by 8dp and hangs the inter-section gap on the last row of a section. The gap rides the row rather than the header because DirectoryListScreen's header is sticky, and padding there pins an empty band under it while scrolling.

Scope

Exactly the three screens where these rows were introduced. The repo's fourth SegmentedListItem call site, MovedOutReportScreen, came from MMA-5782 and is not part of this branch.

The gap fired on every row

app/…/ux/directory/list/DirectoryListScreen.kt:345  ·  as shipped in 149e213ffa

Under Name sort and Birthday sort, every Directory row took the 24dp gap, so one letter group rendered as a column of separated cards rather than as one block. Under household sort with a filter or a search, the same line produced the opposite result and no row took the gap.

How one line does both

  1. The row was asked to identify itself. The shipped test reads two fields off the row it is drawing and infers "I am the last row of my section".

    Changed · shipped in 149e213ffa

    kotlin
    .padding(bottom = if (person.positionInSection == person.sectionSize - 1) 24.dp else 0.dp)
  2. Those two fields are not a section index. They exist to pick a card's rounded corners, and DirectoryListUiState.kt:43 says what they carry: a block is one household, so only the household sorts group rows and every other sort passes (0, 1).
  3. The query hands back literals. field(expression, alias) builds one SELECT column, so the else branch below emits SELECT 0 AS positionInSection, 1 AS sectionSize for every row in the result.

    Unchanged · existing query, shown as evidence

    kotlin

    field("i", "householdOrder", "positionInSection")
    field("h", "memberCount", "sectionSize")
} else {
    field("0", "positionInSection")
    field("1", "sectionSize")
}

    database/member/…/directory/DirectoryDao.kt:170-176

  4. So the test reduces to 0 == 1 - 1 — true for every row that is not in a household sort. And in a household sort sectionSize is memberCount, the household's full size, which a filter or a search does not narrow — so the last visible row of a narrowed household fails the test and takes no gap.

Why the change was needed

A header coming next is what makes a row the end of a section, and the loop at :297-299 already peeks each item to decide whether that item is a header. Reading the answer off the row instead made the test always true.

What the change does

Derives the gap from the same signal that inserts the header, so the two cannot drift apart. The separator that builds those headers, insertSeparators at GetDirectoryListUiStateUseCase.kt:173, is pairwise and cannot stamp the row before it.

Two consequences

peek never triggers a page load, so a row at an unloaded boundary reads null and renders no gap until the next page arrives. And peek(itemCount) is out of range, so the final row of the list now takes no gap — which removes the 24dp of dead space that sat below the last section.
