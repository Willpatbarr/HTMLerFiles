Team Tooling

A shared skill set so 27 juniors produce the same commits, pull requests and bug reports, how it reaches them and stays current, and the project-management tool nobody has picked.

A written convention is read once. A skill runs every time. The repository has 27 junior engineers, no CONTRIBUTING.md, no commit format and no pull request template — which means every commit, PR and bug report is currently a judgement call made 27 different ways.

A skill encodes a decision, it cannot make one

/commit can only enforce a commit format once a format exists. The same is true of /pr and the PR body. Decide the two formats first — they are items 5 and 8 on — then write the skill that applies them. Writing the skill first just moves the argument into the skill file.

/commit

The highest-volume action in the project. Thirty-seven people commit many times a day; a format applied by hand is a format applied unevenly by week three.

The skill should refuse to write a message it cannot justify from the diff, and should split a commit that crosses two crates — which is also how the ownership model stays legible in git log.

/pr

Reads the diff, resolves every path against .github/CODEOWNERS, and names the teams whose review the architecture requires. That is the one merge rule a junior is most likely to miss, because it depends on a file they have no reason to have read.

/bug

A browser engine produces bug reports that cross team lines constantly — a layout bug is often a CSS bug is often an HTML parser bug. A fixed report shape with the crate and owning team on it is what stops a report bouncing between three teams before anyone reads it.

What a skill file looks like

markdown
.claude/skills/commit/SKILL.md
---
name: commit
description: Stage the current change and write a commit message in the
  byui-browser format. Use whenever the user is ready to commit.
---

# Commit

1. Run `git status` and `git diff --staged` to see what is actually changing.
2. Identify the owning crate. One crate per commit; split if the diff crosses two.
3. Write the subject as `<crate>: <imperative summary>`, 60 chars or fewer.
4. Body: what changed and why. Wrap at 72. No "various fixes".
5. Never commit `build.log`, `target/`, or a schema file the migration has not
   finalized.
.claude/ has no owner

Every path without a specific CODEOWNERS rule falls to Scrum of Scrums alone. A skill set that writes commits and opens pull requests for 37 people is closer in blast radius to ci.yml than to a crate, so it deserves a deliberate ownership rule rather than the default one — see , Path Index.

The version field is the release gate, not the git push

Claude Code only hands users a new copy when version in plugin.json changes. Push a skill fix without bumping it and nobody gets it — which is a feature, because it lets you land work in progress on main without shipping it to 37 people mid-sprint.

The corollary is the failure mode to watch for: a fix that everyone swears they pulled and nobody has.

The trust prompt is the one manual step

Repository settings only apply after the person trusts the project folder, which Claude Code asks about the first time they open it. That is one keystroke on first clone, and it is the only interaction in the whole scheme — but it does mean a student who declined the prompt silently has no skills. Worth one line in CONTRIBUTING.md.

Two channels, if you want to test on yourself first

A marketplace is a git repository, so a second marketplace entry pointing at a next branch of the same repo gives you a pre-release channel. Teaching staff track next, the class tracks main, and a skill only reaches 27 juniors after someone has actually used it.

Worth doing from the start rather than retrofitting: a bad /commit skill rolled out to everyone produces a day of malformed history.

Namespacing changes how the skills are invoked

A plugin skill is always called as /plugin-name:skill-name — so /browser-workflow:commit, not /commit. That is deliberate, because it stops two plugins colliding, but it is longer to type and worth choosing a short plugin name for. browser would give /browser:commit.

A committed .claude/skills/ set keeps the bare /commit form. It is the one real advantage that approach has.

Nothing in the repository names a tracker, a board, or a project-management tool. No issue templates, no board referenced from any document, and no ticket ID in any comment. The decision is open.

What the tool actually has to carry here

Nine teams, 37 people, 27 of them juniors, and a dependency structure where four teams sit behind a single unwritten ADR. The binding problem is cross-team sequencing, not estimation or reporting — so the tool is chosen on how well it shows who is blocked on whom, and on how little of a 15-week semester it costs to learn.

The feature being on is not the tool being chosen

A repository has the Projects tab enabled by default, so its presence says nothing. Two directions, and only one of them is the common case

GitHub → tool is a ticket moving to In Review because a pull request opened, and to Done because it merged. Every tool here does this through its own GitHub app, configured with toggles or a rule builder. No workflow file, no secrets, no code.

Tool → GitHub is a workflow step creating or transitioning a ticket from inside a CI run. That needs an action and a token, and it is the rarer case. It is the second table below.

GitHub Projects is the weakest option on exactly this

Its built-in automations cover four things: auto-add items matching a filter, auto-archive, set Status to Done when an issue or pull request closes, and set Status to Done when a pull request merges. The last two are on by default.

There is no built-in workflow for a pull request opened, marked ready for review, or approved. Moving an item to In Review on PR open needs a hand-written GitHub Actions workflow calling the GraphQL API — it is an open request on GitHub's own community discussions, not a setting.

Everything else in the table does it with a toggle.

The half GitHub Projects does get for free

No issue key, no magic word, no branch naming discipline. The pull request is the project item, so the link cannot be forgotten or typo'd — which with 27 juniors is not nothing. Every other tool in the table silently does nothing when someone forgets to put the ID in the branch name.

So the trade is: GitHub Projects cannot move a ticket to In Review automatically, but it also cannot lose a ticket. The others move tickets well when the reference is there.

Verify the free-tier limits before committing to any of them

Jira and Linear both cap their free tiers below what 37 people across 9 teams need, and both move those caps. The numbers in the table are the shape of the answer, not a quote — check each vendor's current pricing page before the decision is recorded.

GitHub Projects

One org-level project, issues and pull requests auto-added from the repository, custom fields for team and status. Nothing new to log into, and the identity is the same one CODEOWNERS already resolves.

Weak at: there is no real dependency graph, and the reporting is thin. Both are workable with a Blocked on field and a saved view.

Jira

The strongest cross-team boards of the three, genuine scrum-of-scrums rollup, and the tool most of these students will meet at work — which is a real teaching argument.

Weak at: cost above ten users, and a configuration burden that lands on whoever administers it. Its advantages are org-scale advantages; this is a 15-week course.

Linear

The best dependency and cycle model of the three, and fast enough that juniors will actually keep it updated — which is the failure mode that kills most course-project boards.

Weak at: the free tier does not reach nine teams, so it is a paid tool here.

Recommendation — GitHub Projects

The project's real risk is coordination, and its coordination facts already live in GitHub: CODEOWNERS says who owns what, the PR says what is in flight, the ADR directory says what is decided. Putting the board anywhere else means those four facts live in two systems and drift.

Two things cut against it, and both are above. It cannot move an item to In Review when a pull request opens — every other tool here does that with a toggle. And Linear's Education Program could make the strongest option free for a year.

The recommendation survives on the grounds that a status column nobody has to maintain by hand is worth less than a board that cannot lose a ticket, and that one source of truth beats two. But it is no longer the obvious answer it looked like before the integrations were checked. If automatic status movement is something the scrum of scrums will actually rely on, pick Linear and send the education email first.

Teams

Nine team charters as written for week 1, plus where each team sits relative to the others in the page-load pipeline.

Nine teams, each with a charter in docs/TEAMS.md. The charters are written for students in week 1 and describe scope in plain terms; the architecture document gives the same teams their crate boundaries.

1. HTML

Builds the HTML parser that turns raw markup into the DOM tree, handling malformed and real-world HTML the way browsers actually have to. Owns the DOM API surface that CSS, JS and Layout query and manipulate.

2. CSS Engine

Builds the CSS parser and the cascade, specificity and inheritance resolution that turns stylesheets plus the DOM into a computed style for every element — the CSSOM. This team determines what the styles are, not where things end up on screen.

3. Layout & Rendering

Takes the DOM and computed styles and builds the layout tree, computing box model, positioning and text flow for every element. Then paints and composites the final pixels, including handling reflows when the page changes.

4. JavaScript Engine

Builds the core JS interpreter and engine: parsing, an execution model, and the runtime that executes scripts against the page. The lowest-level piece the JS APIs and Devtools teams build on top of.

5. JS APIs

Implements the browser-provided APIs scripts call — DOM manipulation methods, fetch, timers, events. Connects the JS Engine to the DOM, Networking and Storage.

6. Networking

Handles fetching resources over HTTP(S): requests, responses, redirects, caching and connection management for pages, scripts, stylesheets and other assets. Feeds parsed responses into the HTML, CSS and JS pipelines.

7. Security & Storage

Implements same-origin policy, cookies and client-side storage such as localStorage and IndexedDB, plus permissions handling such as camera or geolocation. Responsible for making sure pages cannot do things they should not do to each other or to the user.

8. Browser UX

Builds the browser chrome: address bar, tabs, navigation controls, bookmarks, settings. Wires that UI to Networking, HTML, CSS and Layout to actually load and display pages.

9. Devtools

Builds the developer-facing inspection tools: DOM and style inspector, console, network panel, JS debugging. Depends on hooks from nearly every other team, so this group needs close coordination across the whole project.

Branch protection is real, and stricter than the documents claim

A repository ruleset named main has been active since 2026-07-15. It requires a pull request, two approving reviews and Code Owner approval, and it requires the CI job to pass. Nobody can bypass it, administrators included.

Four verdicts elsewhere in this guide were written before that was visible and have been corrected: trunk-based development, the cross-team reviewer rule, the lint gate and the test gate are all enforced, not aspirational.

Ops Brief

Ranked gaps, rules with nothing behind them, contradictions between documents, and what each team is waiting on before it can write real code.

Ranked by what unblocks the most people soonest, not by size. Priority tags follow the OMLR convention: Blocking means something else cannot proceed until it is done.

  1. Blocking1.Write the three ADRs. Process model, IPC format, DOM representation. Architecture §8 names them; docs/adr/ holds a template and nothing else. Every team's first cross-process or cross-crate work queues behind these three decisions, and the ADR path itself needs ten reviewers, so starting late costs twice.
  2. Blocking2.Fill common. Four empty modules that all thirteen other crates depend on. It cannot be filled before the ADRs land, and nothing else can start before it is filled. This is the critical path, and it runs through the highest-review-cost file in the repository.
  3. High3.Add tests/ to the workspace members. One line in Cargo.toml. Without it, cargo test --workspace cannot reach an integration test, and “integration tests that exercise the new path” is a stated merge gate. Cheapest item on this list by a wide margin.
  4. High4.Write CONTRIBUTING.md and a PR template. 27 juniors, a branch naming rule, a cross-team review rule and no written path from clone to merged PR. The PR template is where the cross-team reviewer checklist from §4.1 belongs.
  5. High5.Define a commit message format. The only part of the workflow with no stated convention, in a repository that specifies branch names, review fan-out, ADR approval counts and line width. Pick one, write it in CONTRIBUTING.md, and stop relitigating it in review.

Next five

  1. Medium6.Pin the toolchain. Add rust-toolchain.toml. With -D warnings and a floating stable, a new Clippy lint turns main red with no code change and no owner.
  2. Medium7.Add macOS and Windows to the CI matrix. make release supports three targets; CI compiles one. The shells for the other two will be written against a toolchain nothing exercises.
  3. Medium8.Turn on review-thread resolution, and enable Discussions. The main ruleset is otherwise strong, but an unresolved review comment does not block a merge today. Discussions is named as a coordination channel in §4.3 and is switched off. Two checkboxes.
  4. Medium9.Decide what “experienced engineer” means. Four approval thresholds turn on the phrase. No roster exists, so none of the four is checkable at review time. A GitHub team would make all four mechanical.
  5. Low10.Add #![forbid(unsafe_code)] to crates/browser/src/main.rs. One line. Makes the rule uniform across all fourteen crates and removes the only place unsafe compiles locally.
