That block carries no syntax colour, which the HTML checklist fails. Deliberate: it is rendered output, not source, so a keyword colour in it would name a category the two lines do not have.

The three traps

  • Offset equality, never id equality. The condition is offset equality at the event's own instant — America/Denver and US/Mountain are one zone under two names.
  • When the offsets match, render the device value alone and leave the supporting row as today's label. Never "7:30 PM Central / 7:30 PM Central".

Deferred

1 · Hiding a BUILDING calendar still shows bookings from visible calendars

Truth-table row h. A tester who hides Sunstone Building and expects its bookings to vanish will still see the ones owned by calendars they display.

The strict alternative — make the building check mandatory too, so a facility-booked event needs both its own calendar and its building calendar displayed — is not recommended:

Consequence
Strict intersectionEvery facility-booked event vanishes for a user not subscribed to that meetinghouse
CollateralThat includes events on the user's own displayed ward calendar
Blast radiusLarger than the defect — most users subscribe to units, not buildings

Recommendation: state row h explicitly when asking for sign-off, and let QA decide whether it is a second ticket. Do not fold it into this fix.

2 · The location arm does not restrict to type = 'BUILDING'

Calendar.locationId is nullable on a row of any type, and the location arm matches on locationId alone. CalendarDao.kt:35-40 — the facility picker — restricts to type = 'BUILDING' for the same lookup, so the two disagree about what a location row is.

Adding AND Bldg.type = 'BUILDING' would align them, and today it is almost certainly a no-op. It is left out because it is a second behaviour change riding a query that already needs sign-off, and because "almost certainly" is not a claim this document can verify against server data.

3 · The Calendar table has no indices at all

9.json reports Calendar indices: [], so Calendar.locationId and Calendar.displayed are both unindexed. Event.calendarId is the only index in play. Adding one would need a schema change on an in-flux version, for a table of tens of rows — so nothing is added here, and the EXISTS shape is chosen partly because it keys on the primary key instead.
