Calendar Views — Feature Spec

MMA-5930 · take the PMG calendar prototype from sample data → production · mixed audience

One-Sentence Version

Add four time-grid views (Day / 3-Day / Week / Month) alongside today's agenda list so users can see overlaps and plan around events — wiring the built prototype to real, filterable data behind a rollout flag, matching Google Calendar where it counts.

Overview & Goals

Why

Today the calendar is a list-only agenda — hard to see how events sit across days/weeks or where they overlap. This adds the spatial/time context people expect from a real calendar.

Goals

  • Understand how events relate in time (overlaps, gaps, multi-day) via grids, not a flat list
  • Preserve today's agenda unchanged as the "Schedule" view
  • Ship all views on real, filterable data behind a controlled rollout flag

Primary users

Ward/stake leaders coordinating events (primary); general members viewing unit events (secondary).

Out of scope

Event creation (the detail's "Add to Calendar" device-intent stays), editing/deleting, pinch-to-zoom, arbitrary N-day spans.

Scope — 5 views, v1

The five views

ViewBehavior
ScheduleToday's agenda list, restructured into the "Schedule" view
DaySwipeable single day; hour grid + all-day row + live now-line
3-Day3-day sliding window; live now-line on today
Week7-day grid; live now-line on today
Month4–6 week grid (sized to month); as many chips/day as fit the cell + "N more"; tap day → Day
Key UX decisions

Cross-view behavior

  • Default view: Schedule, every launch (view choice not persisted)
  • Week start: device locale — Month + Week only (3-Day is a sliding window, exempt)
  • Time format: device 12h/24h · Timezone: device timezone
  • Filter: one shared, repo-backed filter — toggling anywhere affects every view
  • Overlaps: shrink/stagger to fit, no cap, no overflow chip (like Google)
  • Empty: Schedule keeps "No events" text; grids show the empty grid only

§6 Restructure

Agenda → Schedule

The agenda list becomes the Schedule view (logic largely unchanged), but shared/common view code must move out of the agenda/ folder into a shared package. Target package structure → technical design doc.

Non-functional

Notes

  • Accessibility: meet the app's existing bar. ⚠️ Time-grid screen-reader support is a known hard problem — no a11y acceptance criteria by design; an accepted risk to name to the PO.
  • Analytics: match today; no new view-usage analytics in v1 (revisit post-rollout)
  • Rollout: behind a controlled flag; mechanics live in the tech design doc
Ship gates (§8)

Required to ship — equal weight

  • Real data in all 5 views behind the flag; sample package removed
  • Filter persists across restarts (repo-backed)
  • No regressions — Schedule preserves agenda behavior (note: its pull-to-refresh gesture was never actually wired; the SmokeTest may need updating after the §6 move)
  • Parity only on unchanged interactions (view-switch, column-packing, drill-down); FRs are truth where they diverge
Data window — resolved

Unbounded nav, display-what's-loaded

Navigation is unbounded — go to any date; grids show whatever data is loaded, empty otherwise.

  • Backward ⚠️: past data will now be synced — a real scope increase (sync change + bounded date-range DAO query). Own ticket + tech design.
  • Forward: grids show whatever's synced; the "Months to show" pref governs the sync horizon; beyond it → empty.
