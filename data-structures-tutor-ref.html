Data Structures Tutor — requirements as built

Twelve structure pages built from the CSE 232 lab headers. What each page must do, what it does, and what was deliberately left out.

Scope · what the tutor is for

Units ordered alphabetically by title.

│ Deliverable form

RequirementPlain HTML pages opened in Chrome from the local folder. Will: rendered in chrome, don't need to worry about obsidian issues and all that
BehaviourNo build step and no server. The pages are opened directly from the folder they live in.
BecauseB — the tutor is revision material for a test, used on one machine by one reader.

│ One page per structure

RequirementA page for each data structure that has a CSE 232 lab, reached from a homepage index.
BehaviourTwelve structure pages and one homepage. The homepage groups the structures as sequential containers, adapters, trees and hashing, and each card carries the structure's lab number and its main operations.

│ Study loop

RequirementOriginal brief — a display that renders the structure, a list of the structure's functions beneath the display, and running a function changes the display.
BehaviourEvery page is display on top, operations underneath, output log at the bottom. Pressing an operation's Run button changes the drawn structure and prints the call and its return value.
BecauseC — the return value alone does not show what moved; the drawing alone does not show what was called.

│ Two things a reader can do

RequirementDrive the structure with its own operations, or rearrange it by hand.
BehaviourBoth are always available. Hand-rearrangement is permitted even where the real structure has no such operation, because setting up a state to study is worth more than protecting the invariant.
SupersedesNothing. Present from the original brief: the boxes should be moveable by clicking and dragging with the mouse

Scope · where the content comes from

Units ordered alphabetically by title.

│ Anything not from a lab is labelled

RequirementA reader must never mistake an invented convenience for a method the lab declares.
BehaviourThe only non-method control on a structure page is reset display, badged not a method. The queue page is badged no lab on the page and on its homepage card.

│ Lab implementations are not trusted

RequirementWill: DO NOT trust the implementations of these methods, I was not the best back in the day and I don't even know what my partner was doing
BehaviourEach page implements the textbook behaviour. Where a lab body disagrees with the textbook, the page follows the textbook and says so on the page.
BecauseB — reproducing a buggy lab would teach the wrong answer before a test.

│ Method names come from the headers

RequirementWill: each lab declares every method that is needed to be present on this tutor. Use the names found in here for methods
BehaviourEvery operation on a structure page is declared in that lab's header. Signatures, default arguments and the header's own section order are carried across unchanged.
Section orderConstruct · Assign · Iterator · Access · Insert · Remove · Status. A page reads in the same order as the file it came from.
Known divergences from the lab bodies

The vector lab reports size() and capacity() as 999 and empty() as true. The hash lab reports bucket_count() as 100 while holding exactly ten buckets, and bucket_size() as 99. Each page does the real thing and states the count it actually holds.

The hash lab's bucket function reinterprets a negative key as an unsigned 64-bit value before taking the remainder, so −12 lands in bucket 4 rather than bucket 8. That behaviour is reproduced exactly and called out on the page, because it is the kind of thing a test asks about.

Scope · left out on purpose

Units ordered alphabetically by title.

│ Implementation detail

RequirementThis document records requirements and behaviour only. Will: don't include any implementation details
BehaviourThe -ref type would normally carry a location line and a code block per unit. Both are dropped here, and the Why bullet block is folded into a Because row.
NoteInterim reading of UB-137 and UB-138 — the invocation selects the plainer reference of settled state rather than the decision-record shape.

│ No queue lab exists

RequirementA queue page was asked for. CSE 232 has no queue lab.
BehaviourThe queue page uses the std::queue names rather than names taken from a header, and is marked as background rather than revision. The page points at the deque as the lab to study beside it.

│ Red-black balancing

RequirementThe BST lab's node carries a red-black flag.
BehaviourThe BST page performs plain insert and erase and does not simulate rebalancing. The page states this rather than implying the shape shown is a balanced one.
BecauseC — the lab body does not settle the intended balancing, and guessing it would be inventing an answer.

│ Staging is one-way

RequirementA node can be dragged from the staging tray into a tree. The reverse is not supported.
BehaviourA misplaced node is removed with Delete and staged again. Dragging a node back to the tray would need a rule for what happens to its children, which is unsettled.

Behaviour · the display panel

Units ordered alphabetically by title.

│ Elements are boxes

RequirementOriginal brief — a series of boxes each representing an entry. the boxes will be a single filled color and a centered number
BehaviourEach element is one box holding one number, filled with a single colour. Linear structures draw a row or a column; tree structures draw a node diagram with edges; the hash page draws ten bucket rows.

│ Scaled to four fifths

RequirementWill: shrink the display by like 20% … just make everything in it smaller to match so nothing is squished
BehaviourBoxes, nodes, text, padding and the side panel all scale together by one fifth, so no element is squeezed relative to another. The panel still spans the full column width.
MeasuredPanel height 492px → 391px on a 1440 × 900 window, a 21 per cent reduction.

│ State readout beside the structure

RequirementThe status operations should be readable without pressing anything.
BehaviourA side panel shows the live value of that structure's status operations — size, empty, and whichever of front, back, top, height and the in-order traversal apply. It updates on every change.

│ Second instance for copy and swap

RequirementCopy constructors, assignment and swap all take another instance, which has to exist somewhere.
BehaviourThe side panel carries an editable list of values standing in for the right-hand side. Swap exchanges it with the displayed structure; the move operations empty it.

Behaviour · the colour scale

Units ordered alphabetically by title.

│ Colour encodes the value

RequirementWill: have the color scale go from red -> orange -> yellow -> green -> blue -> purple and the number range be from -300 to 300
BehaviourA value maps to a position on that spectrum. −300 renders red and +300 renders purple; zero sits mid-spectrum at green. The same number is the same colour on every page.
SupersedesA signed diverging scale, red for negatives and blue for positives with a neutral grey at zero; then the same scale with green replacing blue.

│ Text contrast follows the fill

RequirementDerived — a full spectrum makes one fixed text colour unreadable at one end or the other.
BehaviourEach box takes either white or near-black text, whichever contrasts with its own fill. Yellow through teal fills carry dark text; red, blue and purple carry white.

│ The window is adjustable

RequirementValues clustered near zero are indistinguishable on a 600-wide scale.
BehaviourA multiplier slider zooms the window. At ×1 the ends are exactly −300 and +300; the slider runs ×0.25 to ×5, which is ±1200 down to ±60. A legend bar shows the current mapping and its end values.
Consequence of the ±300 range

The demo values 6, −12 and 38 all fall within about 24 degrees of hue at ×1, so they read as three near-identical greens. That is arithmetic rather than a defect: 38 is six per cent of the way up a 600-wide scale.

The multiplier is the intended remedy — at ×5 the window is ±60 and those same three values separate into green, teal and blue. Changing the seed values or the range itself are the other two ways out, and both remain open.

Behaviour · the two docks

Units ordered alphabetically by title.

│ Both docks collapse

RequirementWill: make both the console output and the display pieces sticky but have them be hideable and showable
BehaviourThe display rides the top edge of the screen, the console rides the bottom, and each collapses to a slim bar that stays reachable. Both states persist across pages and visits.
SupersedesAn unconditional sticky display; then a pin button that toggled stickiness on and off.

│ Console counts its lines when closed

RequirementA console that is closed by default must still signal that something was written to it.
BehaviourThe console bar carries a running count of output lines, so an error from a closed console is still visible as a number that moved.

│ Defaults are display open, console closed

RequirementWill: Have the display shown by default and the console hidden by default
BehaviourA first visit shows the structure and a one-line console bar at the foot of the screen.

│ Sharing the screen

RequirementTwo open docks must not leave the operations with no room.
BehaviourWith both open the display's height cap drops and the console shortens, keeping a usable scrolling band of operations between them. Each dock alone keeps its full size.

│ The hide control costs no space

RequirementWill: make it float underneath the display? that way it doesn't force the display to take up more space
BehaviourThe control hangs off the bottom-right corner of the panel instead of sitting in a bar above it, and clears the panel's own contents so it never covers a control inside.
MeasuredOverhead above the panel 18px, down from about 51px.

Behaviour · direct manipulation

Units ordered alphabetically by title.

│ Boxes drag and snap

RequirementOriginal brief — the boxes should be moveable by clicking and dragging with the mouse. snapping to be in place
BehaviourOn every linear structure a box can be dragged to any position. The others part around it and it snaps to the nearest slot on release. The move is written to the console.

│ Heap nodes swap

RequirementWill: priority queue needs fixing too
BehaviourA heap's shape is fixed by the array's length, so a node has nowhere to move to. Dragging one heap node onto another exchanges the two — the move percolate up and percolate down each make. The heap-property banner updates as the swap lands.
AlsoThe array strip and the heap tree share a selection, so clicking a node in either view highlights the same value in both.

│ Illegal arrangements are allowed

RequirementSetting up a state to study outranks protecting the structure's invariant.
BehaviourHand-rearrangement is permitted wherever it is offered. On the priority queue it deliberately breaks the heap so that heapify has something to repair, and the page says so.

│ Tree nodes re-hang

RequirementWill: let me drag trees in normal mode too
BehaviourDragging a node onto another re-hangs that node and everything under it. Which side it lands on is decided by which half of the target the drop falls on, and the target outlines as the pointer crosses it.
RefusedA move that would make a node its own descendant, and a move onto a child slot that is already occupied. Each is refused with a message and the tree is left untouched.
SupersedesTree nodes could not be dragged at all.

Behaviour · the operation list

Units ordered alphabetically by title.

│ Cards are half the display width

RequirementWill: can make the method boxes take up half the width of the display area instead of a third?
BehaviourExactly two cards to a row, dropping to one below 760px wide. Card heights became uniform as a side effect, because fewer descriptions wrap at the wider size.

│ Every call is logged

RequirementA reader needs the return value, not just the movement.
BehaviourThe console prints the call as written and its return value. Errors print in the error colour. Hand-moves are logged too, marked as drags rather than calls.

│ Operations are grouped as the header groups them

RequirementOriginal brief — under the display should be a list of the common functions of the stack data structure
BehaviourEach operation is a card carrying its signature, a one-line description and a Run button. Cards sit under the header's own section names.

│ Parameters get input fields

RequirementOriginal brief — if a function takes in a parameter than it should have an input field for that parameter
BehaviourOne field per parameter, pre-filled with a usable default. Enter runs the operation. A blank or non-numeric field is refused with a message rather than guessed at.

│ Undefined behaviour is guarded

RequirementSeveral lab operations are undefined on an empty structure.
BehaviourCalling top, front, back or pop on an empty structure logs an error naming the undefined behaviour instead of crashing the page. Out-of-range index access does the same and states the valid range.
BecauseB — naming the undefined case teaches it; crashing the page ends the study session.

Test mode · the workflow

Ordered by the sequence a reader performs. The order is the requirement.

  1. A Test control sits in the top-left corner of the display. Pressing it reveals Start and Submit beside it.
  2. Every operation greys out and gains a checkbox. Ticking one highlights it. Nothing can be run while test mode is on.
  3. Pressing Start prints a numbered list of calls to the console, drawn from the ticked operations, with every ticked operation appearing at least once and a minimum of four calls in total.
  4. The display returns to exactly the state it held before Start, so the printed list is a question rather than a transcript.
  5. The reader reproduces the end state by hand, using the manual controls and dragging.
  6. Pressing Submit compares the structure against the expected answer and either confirms it or asks for another attempt.

│ Arguments are generated, not fixed

RequirementA fixed question is memorised after two runs.
BehaviourArguments are random and checked to be valid for the state at that point in the sequence, so a generated call never relies on an error path. A call that acts on a particular node names that node in the printed line.

│ Toolbar placement and size

RequirementWill: make the test mode buttons a little bigger and put them in the top left of the display window instead of the middle
BehaviourThe toolbar is the first row of the display panel, hard against its top-left corner and spanning the full width above both the structure and the side panel.

Test mode · editing by hand

Units ordered alphabetically by title.

│ Deleting a tree node takes its subtree

RequirementRemoving a node with children must not hand the reader the answer.
BehaviourDelete on a node with children removes the whole subtree, so reproducing an erase means rebuilding the children rather than watching a successor get promoted.

│ Manual creation and removal are required

RequirementWill: because manual manipulation is the way I want the test to work when in test mode manual creation and removal of nodes must be necessary
BehaviourTest mode adds Add and Delete controls and click-to-select. Every call the generator can produce is reproducible with those controls plus dragging.

│ Selection

RequirementThe manual controls act on something, so that something has to be pickable.
BehaviourClicking a box, a node or a bucket entry selects it, and the highlight survives a redraw. Selection is live as soon as Test is pressed, before a question has been started.
SupersedesSelection previously did nothing until Start had been pressed, with no indication of why.

│ Staging zone on the trees

RequirementWill: spawning in a node should not place it in the tree where it would be sorted to or the test doesn't work. ideally a staging zone would be available for it to spawn to so I am forced to drag it into the tree myself
BehaviourAdd puts the node in a staging tray and does not touch the tree. The node enters only by being dragged onto the left or right half of a parent the reader picks. Nothing infers a position from a value.
Empty treeA staged node dropped anywhere in the tree area becomes the root, since there is nothing to drop onto.
SupersedesAdd Left and Add Right buttons, which attached the node to whichever node was selected.

Test mode · how a submission is judged

Units ordered alphabetically by title.

│ Attempts are counted, answers are not shown

RequirementOriginal brief — if the nodes are in the correct positions the test passes, if not the user is prompted to try again
BehaviourA wrong submission reports the attempt number and invites another. The expected state is never printed, so a failed attempt does not end the question.

│ Linear structures are graded on order

RequirementThe arrangement is the thing being tested.
BehaviourThe values and their positions are compared. Capacity, the buffer's front index and other internal state are shown on the page but not graded, since no manual control changes them.

│ Read-only operations contribute nothing

RequirementStated limit rather than a behaviour.
BehaviourTicking a status operation such as size or capacity puts a call in the printed list that needs no manipulation to satisfy. The reader chose it, so it is allowed, but it makes the question shorter than it looks.

│ Staged nodes never count

RequirementA node in the tray is not in the structure.
BehaviourThe tray is excluded from the comparison, and a failed submission says how many nodes are still sitting in it.

│ The answer comes from the page itself

RequirementThe expected result must never disagree with what the page does when the same buttons are pressed.
BehaviourThe generated sequence is run against the page's own operations to derive the answer, and the display is then rewound to its starting state. Console output from that pass is discarded.

│ Trees are graded on shape

RequirementThe right values in the wrong tree is a wrong answer.
BehaviourThe comparison covers the tree's structure including its empty child slots, not just the values it holds. This is what makes placement in a search tree testable at all.

Ordered by family size, largest first. The ordering is not the message.

Why the hash page has no drag

Which bucket a value occupies is decided entirely by the bucket function, so rearranging entries by hand would model something the structure cannot do. Add and Delete are enough to reproduce every call the generator produces for that page.
