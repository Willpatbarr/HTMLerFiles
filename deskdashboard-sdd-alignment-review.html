What Else Matches

Important
  • Modifier surface (Section 9): widget modifiers .id / .title / .size / .priority / .hidden / .refreshRate and dashboard modifiers .theme / .layout / .environment / .refreshRate implemented almost name-for-name, plus a .service() addition.
  • Refresh system (Section 12): shared dashboard clock, per-widget rate override, tick throttling, and no delivery to hidden widgets — all implemented and tested.
  • Theme tokens (Section 10.1): colors, typography, spacing, shape, animation, and default layout match exactly. DarkDesk is the built-in default, per the doc.
  • Layout abstraction (Section 11): the protocol is not grid-committed, exactly as the Evolution Point demands. GridLayout treats .size() as a hint via spans.
  • Hide, don't destroy (Section 11.3): layout switches hide widgets without detaching them — verified by a test.
  • Success criteria (Section 18.1): several are literally encoded as unit tests (inert widgets, removal cancels work, live theme/layout re-injection).
  • Design smells (Section 13): no violations found. No widget references another widget; no service knows about widgets; no widget fetches data directly.

Divergences

Must Know

Resolved: no SwiftUI is intentional, not a departure

DashboardKit is pure Foundation — rendering stops at the WidgetContent / AttachedWidgetSnapshot data contract. Since the UI will be SwiftOpenUI (a SwiftUI-like framework on Linux/Raspberry Pi), a portable core with the UI framework isolated at the edge is the correct architecture.

Part I of the SDD still says "builds on SwiftUI." Its planned Phase 5 revision should reword this to "a SwiftUI-like framework."

Open: the render contract is text-only

WidgetContent is strings and metadata. The gradient-clock HTML prototypes — gradient text, vertical seconds bar, thin fonts — cannot be expressed through it at all.

Either RenderableWidget eventually produces views (via a companion UI target) or WidgetContent grows into a richer renderable description. Decide deliberately.

Open: no publish/observe mechanism

AD-002 says the WidgetModel "publishes"; today snapshots are pulled and the framework never even references the WidgetModel protocol. A SwiftUI-like UI re-renders from observed state, so something must become observable.

Best candidate: keep observation out of the core and put it in the UI adapter (e.g. DashboardRunner republishing snapshots per tick). Needed before the event-driven Music widget.

Minor

  • The Environment omits the refresh clock (SDD Section 8.1 lists it); ticks are pushed via tick() instead. Covered by an Evolution Point — acceptable.
  • No service-push update strategy yet (Section 12) — only clock ticks exist.
  • The executable is a stub: it builds a runner but never calls start() and has no run loop.

Gaps (Expected at This Stage)

Optional
  • Widgets: 1 of 5 MVP widgets (Clock only — no Alarm, Music, Indoor/Outdoor Temperature).
  • Themes: 1 of 4 (DarkDesk). Layouts: 1 of 4 (Grid).
  • The Clock widget has zero test coverage — the test target links only DashboardKit, not the executable. This matters because Section 18.2 designates Clock as the reference widget new developers copy.
  • WidgetPriority and accessoryText are defined but nothing consumes them yet — consistent with the SDD's "leave a TODO" ethos.
  • No Raspberry Pi, hardware, or performance work (Phases 4–5). Package.swift declares no platforms, which keeps the Pi door open.

Remember Only 3 Things

  1. The architecture is faithful: all six frozen decisions are implemented and tested, and the LEGO Test passes.
  2. The pure-Foundation core is the right call for the Linux/SwiftOpenUI target — but the text-only render contract cannot express the clock designs you have already prototyped.
  3. The Clock widget — the designated reference widget — currently has zero tests because of target structure.

What To Do Next

  • Move app widgets into a library target (e.g. DeskDashboardWidgets) so ClockWidget, its model, and its service can be tested.
  • Decide the render-contract strategy: views from a companion UI target vs. a richer WidgetContent — before building the UI adapter.
  • Add a push/observation path (likely in the UI adapter around DashboardRunner) before starting the event-driven Music widget.
  • During the SDD's Phase 5 revision, reword Part I's SwiftUI references to "a SwiftUI-like framework."
