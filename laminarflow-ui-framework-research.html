│What the Kobalte alpha costs

Kobalte seems more dependable from looking around the solid community and their own page, so I'd rather risk that and not have to worry about handrolling the tooltip.

The cost is one install-time lie and one prerelease risk. The alpha's manifest pins solid-js and @solidjs/web to 2.0.0-rc.3 exactly, four releases behind the repo, and npm enforces the manifest rather than the code.

│Drag-and-drop candidates for the board

Kobalte ships no drag-and-drop, so the board is a second pick whatever the UI library is. Solid's version barely constrains it: three of the five candidates carry no framework binding at all, which is why the board question survives the Kobalte decision intact.

LibraryLineFramework binding Who moves the card

The handoff-ref named @zag-js/dnd the candidate on the grounds that it has no peer dependencies. That still measures true, and @atlaskit/pragmatic-drag-and-drop matches it on the same terms while having a stable published line.

│What the refresh test settles

local optimistic write and the worker queued to update the backend database.

That answer decides one thing on its own: the drop has to produce a data change, so a library whose job is moving the DOM node is doing work the signal will immediately redo. sortablejs is the one candidate that works that way, and this is the ground it loses on rather than its age or its API.

It leaves @atlaskit/pragmatic-drag-and-drop and @zag-js/dnd undecided, because both are event-only and both hand the move back to your code. That pick is the document's open question.

What the answer requiresState of the code today

A worker queueing the backend update No queue or outbox exists in LaminarFlow-Backend — see Open
An event carrying source column, target column and slot Supplied by both remaining candidates

│What breaks in the preview builder

i'd like the component lab to work with kobalte as that is how I will be working on the ui elements before I put them in the actual code.

Three of the four components throw when imported into Solid 2's server build, which is the build build-previews.mjs uses. The throw comes from Kobalte's popper module at module scope, so it happens on import and no <Show> guard inside a component avoids it.

│The paste rule, and what it forbids

they don't have to actually update or anything but I do want the code that is previewed to be the code I use in production … am focused on the look of them in the CL.

Promotion stays manual — once a component is done I'd just copy and paste it into the codebase — so nothing generates or imports across the boundary. What the rule costs is that a fence may not contain anything the paste would have to strip.

RuleWhat it forbids inside a fence
Previewed code is production code A lab-only shim, a lab-only prop, a stub standing in for a real import
Promotion is copy-paste Any generated file under src/components/ui, in either direction
./lib/<Name> is a builder path, not a folder Pasting a note's component unedited when it imports a sibling specimen
Kobalte imports resolve from the frontend's node_modules Nothing — @kobalte/core/tooltip is the same import in both places

Interactivity in the previews is not merely deprioritised, it is unavailable: Style HTML Viewer runs pages under a strict local-only Content Security Policy that blocks inline scripts, which is the same constraint that forbids JavaScript in these guides. A preview that needed a click handler would render and then sit dead.

So if I can easily then why not resolves to not in this viewer, and the static jsdom render is the whole of what the lab can show — the look, with states forced by props.
