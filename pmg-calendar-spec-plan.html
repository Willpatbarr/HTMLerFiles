Doc 2 — Technical Design (the "how")

Three items are more than "flip a flag" — this is the real work.

Biggest Unknown

2a · Data-window gap

The repo only syncs current month forward — no past-month data, and no "events between two dates" query. So grid views scrolled backward show empty history.

  • Path A (no past data): cheapest — cap backward nav at current month. No sync/DAO changes.
  • Path B (show history): sync change to fetch past months + a bounded DAO query. Bigger scope.

Undecided — you're checking with team/PO. Doesn't block items 1–3.

Important

2b · Grid filter isn't repo-backed

The grid's calendar filter is in-memory sample data. The agenda filter is already correct — reads getAllSubscribedCalendarsFlow(), toggles via setCalendarDisplayedAsync(). Plan: re-point the grid filter at that same pattern.

Important

2c · Replace the throwaway sample toggles

Two USE_SAMPLE_DATA = true constants exist; the real combine-flows are already written and DI-ready. Plan: delete the constants, gate the grid views behind a Firebase Remote Config boolean in ToolsConfig (mirror isTithingDeclarationsEnabled()). The host VM already injects ToolsConfig.

Cleanup

2d · Delete & tidy

  • Delete ux/calendar/sample/ once flags gone + filter re-backed
  • Fix 2 trivial Detekt FQN violations (java.time.LocalTime.of inline)

No new architecture needed — views plug into the existing CalendarViewMode enum; nav unchanged; Konsist/Koin already satisfied.
