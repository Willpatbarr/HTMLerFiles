Primary key and touch target · open

Copilot's review of PR 2187 left two findings needing a decision. One answer given earlier cited a ticket that covers something else.

│ The collision REPLACE makes silent

database/calendar/…/entities/event/CalendarEventRsvp.kt

database/calendar/…/event/CalendarEventRsvpDao.kt

the key and the conflict strategy that acts on it

kotlin 
@Entity(tableName = "EventRsvp", primaryKeys = ["eventId", "name"])

@Insert(onConflict = OnConflictStrategy.REPLACE)
suspend fun insertAll(rsvps: List<CalendarEventRsvp>)

SQLite's REPLACE deletes the conflicting row before inserting the new one. Two people on event 42 who both display as "Smith, John" cannot coexist: the second insert destroys the first.

│ Why the consequence is worse than a missing row

totalAttendees is derived — rsvpResponses.sumOf { it.headcount } — which is the property argued for earlier so the badge could not disagree with its rows. A collision therefore does not just drop a name, it undercounts the people coming.

That number is what an organizer orders food against, and a father and son sharing a display name in one ward is not an exotic case. Copilot's Critical rating is defensible on impact.

Cut — the walkthrough of how REPLACE differs from IGNORE and ABORT. The mechanism needed one line.

│ Unreachable today

insertAll has no production caller anywhere in the repository. Nothing in the app writes EventRsvp, so every event reads an empty list and no user on any build can reach the collision.

That is the difference between a live defect and a latent one. It also sets the real deadline: before the first writer, not before this merge.

│ Three reasons to fix it with the writer

ReasonConsequence for this PR
The right key depends on a payload nobody has seen If MTMS-151 carries a respondent identifier, keying on it removes the problem entirely. A surrogate key invented now may be discarded
A surrogate key changes the refresh contract REPLACE currently makes a whole-list re-insert idempotent for free. An autogenerated id would need delete-then-insert in one transaction, which belongs in the repository method that writes
The table is empty in every install Room cannot alter a primary key in place, but with zero rows part 2's migration can drop and recreate. No backfill, no data preservation, no risk

The third reason is the strongest and the one Copilot cannot know from the diff.

│ What Copilot is right about

Read the comment's last clause: "…before treating this table as the complete read path." That is a hit on the wording, not only the schema.

The PR body and the entity KDoc both call the read path "complete". It is complete in shape and not collision-safe, so softening the claim is a real concession that costs nothing.

│ Reply draft

Agreed on the mechanism — REPLACE on (eventId, name) would overwrite one of two respondents sharing a display name, and because the attendee total is derived from the rows, that shows up as a silent undercount.

Not fixing it in this PR, for two reasons. Nothing writes EventRsvp in this branch — insertAll has no production caller — so the collision is unreachable on any build today. And the correct key depends on the MTMS-151 payload: if it carries a respondent identifier we key on that, and if it does not we need a surrogate key plus a delete-then-insert refresh inside a transaction, which belongs with the writer rather than ahead of it.

Deferring is near-free here: the table is empty in every install, so part 2's migration can drop and recreate it rather than migrate data. The entity KDoc already records the key as provisional, and this is going on the part-2 ticket.

Fair hit on the wording though — dropping the claim that this is "the complete read path".

│ The modifier that collapses the target

feature/calendar/…/detail/ManageRsvpsTab.kt:271

the info button beside the RSVP Notification Recipients header

kotlin 
IconButton(onClick = onClick, modifier = Modifier.size(24.dp)) {
    Icon(
        imageVector = Icons.Outlined.Info,
        contentDescription = stringResource(CoreR.string.information),
    )
}

Material 3's IconButton is 48dp by default, and that is the whole point of the component: the glyph is 24dp and the surrounding 12dp of empty space is the tap target. Forcing .size(24.dp) collapses the clickable box down to the glyph.

The reason is real. The design frame's title block is 24dp tall, and a 48dp button makes the row 48dp, doubling the height the design gives it.

│ Where 24dp actually stands

"Fails accessibility" is too blunt. The three thresholds disagree with each other.

StandardRequires24dp
WCAG 2.2 SC 2.5.8, level AA24 × 24 minimum Passes, exactly at the floor
WCAG 2.1 SC 2.5.5, level AAA44 × 44Fails
Android and Material guidance48dpFails

Copilot's phrase "the platform's 48dp touch target" is the third row. This is not a WCAG AA violation.

│ Three options, preference order

Ordered by preference, not by cost. The ordering is the message.

#OptionWhat it costs
1 Fix it here — let the IconButton keep its 48dp bounds and stop the row growing, either by giving the title Row a fixed height and letting the button overflow it, or by moving the info affordance into a row that already has vertical space A visual pass against the frame. That is the real expense, not the code
2 File a ticket for app-wide sub-48dp targets, covering the chips and this button, then cite that ticket in the comment and the reply Honest, and it creates the thing that is currently missing. Leaves the deviation shipped in the meantime
3 Keep 24dp and argue it meets WCAG 2.2 AA Defensible on the standard. Still the only IconButton in the app doing it, which is what gets re-flagged

Whichever is chosen, the comment and the commit message need correcting — the wrong ticket reference is independent of the design decision.
