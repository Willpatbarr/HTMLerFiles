3.4.1 — why the migration-borne seed counts

The fresh-install path already runs migrations twice over: ensureSchema in main.go applies them at startup, and TestMain in internal/document applies them to an empty database on every test run.

The INSERT INTO workspace in 0003 is therefore already on the first-run path, inside the same transaction as the CREATE TABLE. Go bootstrap logic would be a second mechanism for the same fact, needing its own idempotency check to avoid a second row on every restart.

3.4.2 — the reason is already in the file

0003 says an index would be “guessing at a query pattern that does not exist” and names the ticket that should add the index — the one introducing workspace-scoped reads. Adding an index under LAM-11 would overrule that decision without new evidence.

3.4.3 — what makes workspace.name different from team.name

LAM-12 asks for uniqueness on (workspace_id, name) because a workspace holds many teams. A self-hosted instance holds one workspace, so there is no second name to collide with. Note the asymmetry rather than resolving it.

3.4.4 — what recording it looks like

Step 8. A docs/changes/LAM-11-changes.md pair saying LAM-11 was satisfied by 0003, and why the seed was left in the migration, is the deliverable. A future reader finding LAM-11 closed with no commit needs somewhere to look.

4.1The Why Block

sql
-- LAM-NN: the <table> table.
--
-- <what this table is for, and what must not be assumed about it>
  • Everything above the Up marker is ignored by the runner, so the why block is free space.
  • Write what the code cannot say: intent, and the assumption a reader would otherwise make. 0003's block exists to say “nothing may assume there is exactly one workspace”.

4.2The Up Marker And CREATE TABLE

sql
-- +migrate Up

CREATE TABLE <table> (
    id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    name       text        NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);
  • Both markers are required. The runner rejects a file missing either marker.
  • uuid PK with gen_random_uuid(), and timestamptz never timestamp, are what 0001 and 0003 both do.

4.3The Foreign Key Column

sql
    workspace_id uuid NOT NULL REFERENCES workspace(id) ON DELETE RESTRICT,
  • ON DELETE RESTRICT is 0003's choice for document.workspace_id. Pick RESTRICT or CASCADE deliberately and say which in the why block.
Expand and contractNOT NULL inline is safe only because the table is new and has no rows. Adding a NOT NULL foreign key to an existing table is the expand-and-contract case in migrations/README.md, and is exactly what 0003 got wrong under LAM-4.

4.4The Index Decision

sql
-- No index on <column> yet. <the query pattern that does not exist yet>,
-- so indexing now would be guessing. Add it with the ticket that
-- introduces <the reads that need it>.
  • The repo's convention is to write the decision down either way, so the absence of an index does not read as an oversight.
  • A UNIQUE constraint is a different question from an index and usually earns a yes — (parent_id, name) where the ticket calls for one.

4.5The Down Marker And Drops

sql
-- +migrate Down

DROP TABLE <table>;
  • Order matters when more than one object is dropped: anything holding a reference goes before the thing referenced. 0003 drops document.workspace_id before workspace.
  • TestRealMigrationsApplyToAnEmptyDatabase reverses every real migration on every run, so a Down section that does not work fails the build.

4.6COMMENT ON TABLE, When The Role Is Unclear

sql
COMMENT ON TABLE <table> IS
    '<source of truth, or derived and disposable>';
  • 0004 set this precedent for document and search_index, so someone opening psql before reading the Go sees which table is authoritative.
  • Only worth it where the table is derived, disposable, or otherwise easy to mistake for a source of truth. A plain hierarchy table needs no comment.
  • If the comment is added, mirror the comment in the Down section with COMMENT ON TABLE <table> IS NULL;.

Step 5 — Write the tests the migration earns

Skip for LAM-11. Migration 0003 adds no constraint that LAM-11 changes.

5.1 — what is already covered, for free

TestCovers
TestRealMigrationsApplyToAnEmptyDatabaseEvery migration applies to an empty database
The same test's Down halfEvery migration reverses cleanly
internal/document TestMainThe fresh-install path a self-hosted user takes

Do not write a test asserting the table exists — TestRealMigrationsApplyToAnEmptyDatabase already asserts every migration applies.

5.2 — the one test per ticket worth writing

The constraint the migration actually claims, asserted by trying to violate it: an orphan foreign key, a duplicate on the UNIQUE pair, a null in a NOT NULL column. A constraint with no test is a comment.

tableExists and newPool already exist in internal/migrate/runner_test.go and are the nearest helpers.

5.3 — where the test goes: internal/migrate

Settled under LAM-12, and it holds for every remaining schema ticket. One file per table, internal/migrate/schema_<table>_test.go, so a ticket adds a file rather than editing a shared one.

The reason is sequencing: the constraint gets asserted before any Go code that uses the constrained table exists. Waiting for an owning package would mean the constraint ships untested and stays untested until some later ticket happens to need it.

LAM-27 still owns the broad hierarchy integration tests. These are narrower: one table's own constraints, asserted by trying to violate each one.

Say why the file lives thereinternal/migrate is deliberately generic — the package doc notes it has no dependency on migrations outside of tests, which is what lets the runner serve any migration set. real_test.go crosses that boundary on purpose and explains itself in a comment. A schema test file should carry the same note.

Step 8 — Write down what outlives the ticket

Four places, three of which are usually the wrong one. Pick deliberately.

DestinationEarns a write when
A comment on the Linear issueThe ticket produced no code change
docs/changes/LAM-NN-changes.md + .htmlThe ticket changed code
migrations/README.mdThe ticket taught a rule about migrations generally
docs/adr/NNNN-*.mdA decision is still in force and is not visible in the code
LaminarFlowXMLWIkiGo code changed. A SQL-only ticket updates nothing
  • Add the docs/changes/README.md table row alongside the pair. The table is the index and is easy to forget.
  • Architecture and product decisions spanning both repos are Linear documents on E-LAM-0000, not ADRs. docs/adr/README.md states that boundary.
LAM-11's write is the Linear comment, not a changes pairdocs/changes/ records why a change was made, and LAM-11 makes none — a file describing a non-change misleads whoever finds it. The comment carries Step 3.4.1's reasoning: LAM-11 was satisfied by migration 0003, the seed stayed in the migration rather than moving into Go bootstrap logic, and the index was deferred deliberately.
