Settings Icon Background Colors — Theme-Adaptive Options

The colored circles behind the Settings icons are hardcoded for light mode. This guide compares five ways to make them follow the OS theme — so your team can pick one.

One-Sentence Version

Make the icon-color getters theme-aware, then choose: keep all 9 distinct colors (more work) or reuse a smaller palette the app already has (less work, fewer colors).

Must Know

The Problem

  • 9 Settings categories, each an icon inside a 40dp colored circle.
  • Colors are hardcoded light pastels — they don't flip for dark mode and ignore Material You.
  • Source: two plain getters in SettingsUiState.kt — iconBackground (line 183) and iconTint (line 196).
  • Render site: SettingsScreen.kt:192.
  • The code already flags the fix: "Stage 3 → theme tokens (convert these getters to @Composable)."

Proven pattern in-app: ReorientButton.kt puts an icon on primaryContainer with an onPrimaryContainer tint and adapts to the theme correctly.

Must Know

Shared Prerequisite (all options)

Convert the two getters at SettingsUiState.kt:183 and :196 from plain properties to @Composable getters so they can read MaterialTheme.colorScheme / AppTheme.extendedColors.

The render site at SettingsScreen.kt:192 needs no structural change — only the color sources differ. This step is identical no matter which option you pick.

The 5 Options

Direction 1 keeps all 9 colors distinct. Direction 2 accepts a smaller cohesive palette. Option E is a hybrid.

Direction 1 · keep 9 distinct

A — New "category accent" tokens

Add 9 light/dark pairs to the design system (extend ExtendedColorScheme / LocalAppColors).

Gain: all 9 distinct, full light/dark + contrast tiers, designer-controlled.

Give up: highest effort; hand-author + contrast-check ~9 dark pairs.

The literal "Stage 3 → theme tokens" path.

Direction 1 · keep 9 distinct

B — Derive dark variants in code

Keep the pastels; transform them at render time when isSystemInDarkTheme().

Gain: all 9 distinct, no design-system changes, low–med effort.

Give up: no contrast tiers / dynamic color; WCAG risk on some hues.

Direction 2 · cohesive palette

C — Reuse ExtendedColorScheme

Map categories to existing families: info / alert / success / privacy / warning.

Gain: light/dark + contrast tiers free, guaranteed-accessible, lowest effort.

Give up: only ≤5 colors — categories share; no dynamic color.

Most directly reuses colors we already have.

Direction 2 · cohesive palette

D — Reuse Material 3 roles

primaryContainer / secondaryContainer / tertiaryContainer / surfaceVariant + on* tints.

Gain: light/dark + contrast + dynamic color (Material You), lowest effort.

Give up: only 3–4 distinct colors — least "iOS-distinct".

Hybrid

E — Harmonized brand hues

9 fixed brand hues run through MaterialColors.harmonize(color, primary) so they shift toward the active theme and feel unified.

Gain: all 9 stay recognizable but cohesive in both themes. Give up: medium effort, still needs light/dark base handling, only partial contrast/dynamic awareness.

Decision Helper

Preserve the distinct iOS look → pick A (or B for a cheaper, riskier version).
Lowest effort + guaranteed accessibility → pick C.
Maximal OS integration (Material You) → pick D.

The "Stage 3 → theme tokens" comment already leans toward A and C as the most on-plan choices.

Optional · do after choosing

How To Verify

  1. Build & run: ./gradlew :app:assembleDebug, then open Settings.
  2. Toggle device light → dark (and the in-app override); confirm every circle's fill + icon tint flip with legible contrast.
  3. For D / E: enable dynamic color on Android 12+ and confirm the circles re-tint to the wallpaper.
  4. Spot-check WCAG contrast per background/tint pair — especially B and E.
  5. Add a Compose @Preview with both light and dark uiMode.
